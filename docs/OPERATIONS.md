# Operations runbook

Short notes for people deploying or scripting against Mind Weave.

## Local development troubleshooting

Applies to **`make dev`**, **`./startdev.sh`**, and manual FastAPI + Vite setups.

- **Ports already in use** — **`8000` (FastAPI)** or **`5173` (Vite)**: find listeners (`lsof -nP -iTCP:8000 -sTCP:LISTEN` on macOS; see [backend/README.md — Troubleshooting](../backend/README.md#troubleshooting)) and stop the stale process—two servers on one port yields confusing 404/CORS shells.
- **Browser shows CORS or “failed to fetch”** — Ensure the browser origin matches an entry echoed under **CORS allowed origins** — use **`http://127.0.0.1:5173` vs `http://localhost:5173`** consistently after login; mismatched **`VITE_API_BASE`** vs **`CORS_ORIGINS`** is common when mixing origins by hand ([frontend/README.md](../frontend/README.md#api-base-url)).
- **Phone / LAN cannot load the UI** — Trust the LAN, confirm **`make dev`** printed a LAN IP for the host machine, firewall allows **8000/5173**, and you used the **`http://<LAN>:…`** URLs on the remote device—not `localhost`.
- **`make dev` + Google OAuth** — Google rejects redirect hosts that are bare **private IPs**; use password login over LAN or a path with a public hostname (**[DEPLOYMENT_AND_NETWORK.md](DEPLOYMENT_AND_NETWORK.md)** — Path B).
- **`uv` fails / “No `pyproject.toml`” from repo root** — Use **`uv --project backend …`** or **`cd backend`** ([CONTRIBUTING.md](../CONTRIBUTING.md)).
- **Frontend deps missing / `vite` unknown** — Run **`npm install`** in **`frontend/`** once ([frontend/README.md](../frontend/README.md#setup--running)).

Maintainability: **`shellcheck startdev.sh`** should stay clean — run after editing the launcher.

## After a backend deploy — auth (JWT)

The API validates JWT shape on every request:

- **Access tokens** must include **`typ: "access"`**.
- **Refresh tokens** must include a string **`jti`** (used for rotation and revocation).

**What operators should expect**

- **No migration** on the server for tokens issued under the old rules. Invalid tokens are rejected until the client gets a new pair.
- **Bundled SPA (cookies):** Users who only have a stale access cookie may see **401** until they **sign in again** or complete a **refresh** (whichever your deployment uses). New logins and refreshes issue compliant tokens automatically.
- **Scripts / API clients using `Authorization: Bearer`:** If you store a long-lived access JWT from before the change, **401** is expected after deploy. **Obtain a new token** via your login or refresh flow and update stored credentials.

Step-by-step overlap with release wording: [CHANGELOG.md](../CHANGELOG.md) (section **0.2.0**).

## After a backend deploy — DB (`palettes.slug`)

Releases that add **`palettes.slug`** require **`alembic upgrade head`** before relying on built-in sync or **`GET /api/v1/palettes/by-slug/{slug}`**. The migration backfills slugs for existing system presets by **display name**.

## Workflow runs — Gmail time filters (`execution_time_zone`)

`POST /api/v1/workflow-definitions/{id}/run` and **`POST …/workflow-definitions/{id}/runs`** (enqueue for Build / SSE) accept an optional JSON field **`execution_time_zone`** (IANA name). When a user’s **`workflow_time_zone`** profile setting is **`system`** (or unset), the executor uses this value for Gmail **`after:`** / **`before:`** calendar-day derivation; API-only clients that omit it get **UTC** calendar days for that case. Fixed IANA values in **`User.settings.workflow_time_zone`** win over the request body. See [docs/WORKFLOW_SKILLS.md](WORKFLOW_SKILLS.md).

## Workflow execution limits (TTL, step budget, loops, nesting)

Saved graphs may carry optional top-level **`execution_limits`**; **`User.settings.workflow_execution_limits_prefs`** (optional sparse object validated on **`PUT /api/v1/auth/me`**) can fill in gaps for that user above deployment defaults; each **`WorkflowRunRequest`** may also specify **`execution_limits`** for that run alone. Layers merge (**run** wins over **saved graph** over **user prefs** over **deployment defaults**) and **must not exceed operator ceilings** — otherwise the API returns **422** before execution. Persisted **`WorkflowRun`** rows store the resolved caps on **`execution_limits_effective`**. The SPA configures prefs under **My Settings → System Settings** (alongside **`max_concurrent_lm_studio_calls`**). Operators tune defaults and ceilings with env vars in [`backend/app/core/config.py`](../backend/app/core/config.py):

- **`WORKFLOW_EXECUTION_DEFAULT_TTL_SECONDS`** / **`WORKFLOW_EXECUTION_CEILING_TTL_SECONDS`** — wall-clock **`asyncio.wait_for`** around the DAG.
- **`WORKFLOW_EXECUTION_DEFAULT_MAX_NODE_EXECUTIONS`** / **`WORKFLOW_EXECUTION_CEILING_MAX_NODE_EXECUTIONS`** — global counted node completions/failures per run (**aligned with streamed `node.completed` / `node.failed`**).
- **`WORKFLOW_EXECUTION_DEFAULT_MAX_LOOP_ITERATIONS`** / **`WORKFLOW_EXECUTION_CEILING_MAX_LOOP_ITERATIONS`** — **list length vs For Loop input** guard (reject before body execution when the wired list is too long).
- **`WORKFLOW_EXECUTION_DEFAULT_MAX_NESTED_DEPTH`** / **`WORKFLOW_EXECUTION_CEILING_MAX_NESTED_DEPTH`** — nested **Workflow** node depth guard.
- **`WORKFLOW_DEFAULT_LOOP_BATCH_SIZE`** / **`WORKFLOW_MAX_LOOP_BATCH_SIZE_CEILING`** — defaults and ceiling for **`for_loop`** **`iteration_mode: batched`**.

**Preflight (static step budget)** — The same run endpoints evaluate a conservative upper bound on counted node steps (For Loop iterations from **list** primitives, per-loop **`max_iterations`**, merged **`max_loop_iterations`**). The API returns **422** with **`error: preflight_blocked`** only when that bound **clearly** exceeds **`max_node_executions`** without ambiguous inputs; **422** with **`error: preflight_warnings`** means the client should confirm and retry with **`acknowledge_preflight_warnings: true`** (uncertain loop lists or graphs that contain nested **Workflow** nodes). Implementation: [`execution_preflight.py`](../backend/app/domain/execution_preflight.py).

**`GET /api/v1/workflow-execution-limits/`** exposes **defaults**, **ceilings**, and **`max_loop_batch_size`** for editor validation without guessing env on the SPA host.

See [docs/ARCHITECTURE.md](ARCHITECTURE.md) and [backend/README.md](../backend/README.md#api-reference).

## Workflow `fetch_url` env

The **`fetch_url`** skill issues HTTP requests from the **API process** (see the **Fetch URL** subsection in [WORKFLOW_SKILLS.md](WORKFLOW_SKILLS.md)). Relevant environment variables in [`backend/app/core/config.py`](../backend/app/core/config.py):

- **`FETCH_URL_DEFAULT_TIMEOUT_MS`** — per-request timeout when the node does not set **`timeout_ms`** (default 30000).
- **`FETCH_URL_MAX_BODY_BYTES`** — maximum bytes read for the response body (default 2 MiB); larger bodies produce a structured error object on the **successful** step output.

## `capture_url_snapshot` — Playwright

The **`capture_url_snapshot`** skill uses **Playwright** to launch **headless Chromium** in the **API process**. Install the **Python** package with the backend optional extra **`url-snapshot`** (e.g. from `backend/`: **`uv sync --extra url-snapshot`**, or add **`--extra dev`** for development tools). On first deploy, install the browser binary (per machine or container image):

- From `backend/`: `uv run playwright install chromium` (or bake the same in your **Dockerfile** / CI image).

Relevant settings in [`backend/app/core/config.py`](../backend/app/core/config.py):

- **`CAPTURE_URL_SNAPSHOT_DEFAULT_TIMEOUT_MS`** — navigation/screenshot budget when the node omits **`timeout_ms`**.
- **`CAPTURE_URL_SNAPSHOT_DEFAULT_VIEWPORT_WIDTH`** / **`CAPTURE_URL_SNAPSHOT_DEFAULT_VIEWPORT_HEIGHT`** — viewport when the node omits dimensions.
- **`CAPTURE_URL_SNAPSHOT_MAX_PNG_BYTES`** — reject oversized PNG results with a structured **`error`** on the **successful** step path.

Resource notes: each capture launches a **browser** and loads the full page; **full-page** screenshots can be large. Consider caps, process isolation, and the same **trusted graph** / **SSRF** expectations as **`fetch_url`**.

## Workflow runs — forced outputs (`output_overrides`)

**`POST …/run`** and **`POST …/runs`** accept optional **`output_overrides`**: a map of **`node_id` → JSON value** matching that step’s output type. Those nodes are **not executed**; the value is injected, and run logs include **`details.forced_output`**. Overrides are **not** allowed for nodes inside **for-loop bodies** (v1). Nested **Workflow** nodes can use child graph node ids when the referenced definition is reachable from the root graph. Invalid keys or types return **422** before execution. See [docs/ARCHITECTURE.md](ARCHITECTURE.md). In the **Workflow Editor**, open **Explorer**, select the step, expand **Last Run**, and use **Override output** — this works **before** the workflow has ever been run on the canvas (same session overrides are sent with **Run**).

## Workflow run storage and cleanup

- **Retention** — On API startup, runs older than **`WORKFLOW_RUN_LOG_RETENTION_DAYS`** (default **90**, `0` = disabled) are deleted with their **`node_run_logs`** rows using **bulk `DELETE`** statements (not per-row ORM deletes). See the env table in [backend README](../backend/README.md#environment-variables).
- **Manual deletion** — Users can remove runs from the app (**Build → Replays**) without waiting for retention: per-row trash (inline **Delete** / **Cancel**) or **multi-select** plus **Delete selected** (then **Delete all** / **Cancel**). Each removal still uses **`DELETE /api/v1/workflow-definitions/{id}/runs/{run_id}`**; bulk cleanup in the UI is implemented as sequential calls. Only runs **they started** on **their** workflows can be listed or deleted.

## Workspace turns and replay

- **Retention** — V1 does **not** purge **`workspace_turns`** or **`workspace_replays`** automatically; plan capacity or prune manually if needed. See [WORKSPACE.md](WORKSPACE.md).

## SQLite WAL mode

The backend enables **WAL (Write-Ahead Logging)** mode automatically on every SQLite connection ([`db.py`](../backend/app/persistence/db.py)). WAL allows concurrent readers and writers, so startup seed writes do not block incoming API requests.

**Operator notes:**

- The WAL file (`mindweave.db-wal`) and shared-memory file (`mindweave.db-shm`) appear alongside the database. They are managed by SQLite and should not be deleted while the server is running.
- WAL mode persists across connections once set; the pragma is re-executed on connect as a safety net.
- If you move the database file, copy all three files (`*.db`, `*.db-wal`, `*.db-shm`) together, or run `PRAGMA wal_checkpoint(TRUNCATE)` first to fold the WAL back into the main file.

## Multi-instance / reverse proxy

In-process **per-IP rate limits** (auth POST routes, workflow **`POST …/run`**, **`POST …/runs`**, and **`POST .../workspaces/.../turns/stream`**) apply **per API process**. Multiple workers or replicas do **not** share counters; put a **reverse proxy or shared limiter** in front if you need global limits. Env vars and format (`N/minute` only): [backend README environment table](../backend/README.md#environment-variables).

**TLS, public hostnames, Google OAuth, LAN vs tunnel:** See **[DEPLOYMENT_AND_NETWORK.md](DEPLOYMENT_AND_NETWORK.md)** for choosing localhost vs LAN vs domain + HTTPS vs tunnel, operator checklists (DNS, router, Google Cloud), and example [nginx config](examples/nginx/mind-weave.conf.example).

## Debugging workflows (graphs and runs)

Use this when correlating a workflow or run with the database, support, or offline analysis.

- **Editor** — With a workflow open and **nothing** selected on the canvas, the **Explorer** tab shows **workflow definition UUID**, optional **last run id** (current session), and **Copy debug JSON** ([`WorkflowExplorerWorkflowMetadata.tsx`](../frontend/src/components/workflow-editor/WorkflowExplorerWorkflowMetadata.tsx)).
- **Workflow JSON (share / debug)** — **Build** toolbar: **Export** downloads a **workflow bundle** (`kind: mind_weave_workflow_bundle_export`): the open workflow plus **transitive** nested workflows and referenced **personas**, **structures**, **documents**, and user-owned **palettes** (built-in palettes are recorded as **`palette_slug`** on each definition for remap on import). **Copy** (clipboard icon) copies the same bundle. Export **fails** if any nested workflow or referenced resource cannot be loaded. **Image / voice / audio** artifact ids are **not** embedded—`export_warnings` lists them; re-upload or re-select after import. **Google** workflow skill **nodes** are in the graph; **OAuth** is per user—importer must connect **Google for workflows** under My Settings before runs. **Workflows** list: **Import** accepts a bundle or legacy single-workflow export (`mind_weave_workflow_export` v1); bundle import recreates dependencies and remaps ids. Root workflow name is suffixed ` (imported)` when needed. Implementation: [`workflowBundleImportExport.ts`](../frontend/src/domain/workflowBundleImportExport.ts), [`executeWorkflowBundleImport.ts`](../frontend/src/domain/executeWorkflowBundleImport.ts), [`workflowImportExport.ts`](../frontend/src/domain/workflowImportExport.ts) (single-workflow v1 parse only).
- **REST** — `GET /api/v1/workflow-definitions/{id}` returns the full graph; `GET /api/v1/workflow-definitions/{id}/runs/{run_id}/logs` returns per-step logs (redacted; see [WORKFLOW_SKILLS.md](WORKFLOW_SKILLS.md)).
- **Offline script (graph validation)** — From the `backend/` directory, run `uv run python scripts/analyze_workflow_definition.py --workflow-id <uuid>` against the configured **`DATABASE_URL`**. That loads **`workflow_definitions.graph`**: **the same JSON** the API serves as **`GET /api/v1/workflow-definitions/{id}`** (Workflow Editor parity with the SPA). It prints a **node id → label** table (same labels as the canvas), runs **`validate_for_loop_bodies`** and **`validate_for_loop_end_configuration`** (same rules as [`graph.py`](../backend/app/domain/workflow_executor/graph.py)), and can dump the raw graph with **`--json`**. Add **`--run-id <uuid>`** to list **`node_run_logs`** for that run (often empty when validation fails before any step); each line includes **`label`** when known. Add **`--edges`** to print each edge’s **`source_handle`** / **`target_handle`** (useful when debugging React Flow handle mismatches). Add **`--wiring-issues`** to list **offline handle mismatches** (missing nodes, unknown Start/Stop handles, common static steps; nested **Workflow** nodes defer to the SPA **Graph issues** panel). Add **`--summarize`** for a compact **Upsert Document** view: node **id**/**label**, **all edges targeting** those nodes, and trimmed **`required_inputs`** **name**/ **content** inline excerpts (privacy-friendly truncation). Example id for correlation with screenshots or docs: **`f2df2602-ba7a-4bad-b1cd-af0d69509766`** — use it **only if** that definition exists under **your** **`DATABASE_URL`**. When comparing to the canvas, remember **Stop** has a **`trigger`** input (schedule) and a **data** input whose id matches **`required_outputs[0].key`** (default **`output`**); final payloads must use the **data** output from upstream (e.g. **`output`** on utilities), not **`signal_out`** into the data handle.
- **Graph wiring issues (editor)** — When persisted edges reference handles that are not on the node cards (e.g. **`sandbox_tick`** on **Start** after outputs were cleared, **Stop** **`output`** when the data handle was renamed, **For Loop End** export keys), **Run Logs** lists **Graph issues** at the top (amber tab indicator); **Explorer** shows the same panel when **nothing** is selected on the canvas. Broken edges are **hidden from the canvas** but still saved until you **Delete connection** or fix slots in the inspector; Save and Run remain allowed. See **Workflow editor graph wiring issues** in [ARCHITECTURE.md](ARCHITECTURE.md).
- **SPA parity persisted run — HTTP (`POST /runs` + `GET …/events`)** — From `backend/`, `uv run python scripts/run_persisted_workflow_stream_http_e2e.py --workflow-id <uuid> [--username … --password …]` logs in (**same cookie/session model as the browser**), **GET** **`/api/v1/workflow-definitions/{id}`**, then **POST** **`…/workflow-definitions/{id}/runs`** and **GET** **`/api/v1/workflow-runs/{run_id}/events`** (**SSE**, same handshake as **`ApiClient.startWorkflowRun`** + event subscription — see [`frontend/src/api/client.ts`](../frontend/src/api/client.ts)). By default the script spins a temporary **uvicorn** on **`127.0.0.1`**; pass **`--base-url`** to drive an already-running API. Optional **`--assert-upsert-body-non-empty`** asserts **Upsert** steps produced non-empty **`output.markdown`** (and checks **`GET /api/v1/documents/{id}`** **`body`** when **document_id** is present); use **`--upsert-node-id`** when multiple **Upsert Document** utilities exist; on failure it prints edges into that node — compare with **`analyze_workflow_definition.py --summarize`**. Use credentials for whichever **tenant user owns** **`workflow_definitions.id`** (**404** otherwise). Prefer this over **`run_upsert_document_http_e2e.py`** when reproducing **Workflow Editor** behavior on a **real saved graph**; keep the latter for **synthetic** **`POST …/run`** micro-regressions (see next bullet).
- **Offline script (NDJSON to stdout)** — From `backend/`, `uv run python scripts/run_workflow_stream.py --workflow-id <uuid>` enqueues an in-process persisted run (**`WorkflowExecutor.execute_scheduled_run`**) and prints **line-oriented NDJSON-shaped records** to stdout (compat with historic stream clients; mirrors **`GET …/events`** payloads). It **`chdir`s to `backend/`** before loading config so **`backend/.env`**, **`LMSTUDIO_BASE_URL`**, and **`sqlite:///./mindweave.db`** match a normal **`uvicorn`** process (running from the repo root without this would load the wrong DB or default LM URL). It prints **`cwd`**, **`LMSTUDIO_BASE_URL`**, and **`DATABASE_URL`** to **stderr** on startup—LM Studio requests use the same code as the API; if LM Studio shows no traffic, compare that line to the API’s effective config and fix reachability. **Use `uv run` as shown** (`source .venv/activate` is not required; `uv run` already uses the project env). **AI agents / CI / remote runners** often execute in a **different network namespace** than your laptop: **`127.0.0.1`** and LAN IPs such as **`10.x.x.x`** point at *that* host, not your machine, so LM Studio may be unreachable there even when the same command works in **your** terminal. For real LM traffic, run the script **locally** (or on a host that can reach **`LMSTUDIO_BASE_URL`**). Pass inputs like **`--input-json '{"input_overrides":{"user_input":"hello"}}'`** (same optional keys as the API: **`output_overrides`**, **`execution_time_zone`**, **`execution_limits`**). Optional **`--user-id`** defaults to the workflow owner, else the first user row.
- **Offline script (books.toscrape sample: `fetch_url` + `html_parse_basic`)** — From `backend/`, `uv run python scripts/run_books_toscrape_fetch_parse_sample.py` **inserts a workflow** (Start → **Fetch URL** for `https://books.toscrape.com/` with **`cache_policy: bypass`** → **Dictionary value by key** on `body` → **HTML parse basic** → Stop), **executes** it once with a **real** HTTP GET, and **prints the parse result** (title, `text_blocks`, `links`) to stdout. A **workflow id** is printed to **stderr** for reuse with **`run_workflow_stream.py`**. The definition stays in **`DATABASE_URL`** so you can open it in the editor; **`--cleanup`** removes the user and definition created for that run. **No** LLM; requires outbound network. On the default catalog page, **`text_blocks` is many dozens of `{tag, text}` objects** (breadcrumbs, sidebar category links, per-book `article` cards, footer copy, and pagination) rather than a single bloated `div`; nested lists do not add a separate parent `li` line that repeats every child category in one string. Use **HTML parse basic** to feed meaningful chunks to downstream steps, or add **`data.content_root_css`** to narrow scope. In the editor you can set **`data.granularity`** (e.g. `list_items`) and **`data.content_root_css`** (e.g. a selector for the main column) on **HTML parse basic** to experiment without editing the sample script.
- **Offline script (`multimodal_llm` sample)** — From `backend/`, `uv run python scripts/run_multimodal_llm_sample.py` **seeds** a tiny **PNG** row in **`url_snapshot_artifacts`**, inserts a minimal workflow (**List** + **String** primitives → **Multimodal LLM** → **Stop**), and runs **`WorkflowExecutor`** once. **By default** the script **mocks** [`LMStudioProvider`](../backend/app/providers/lmstudio.py) so **no HTTP** is sent to LM Studio (safe for CI/agents). Pass **`--real-llm`** only on a machine where **`LMSTUDIO_BASE_URL`** reaches a running LM Studio instance with a **vision-capable** model loaded matching the Persona default (or set a **`model`** override on the node in the DB/editor). A **workflow id** is printed to **stderr** for **`run_workflow_stream.py`**; **`--cleanup`** deletes the temporary user, artifact, and workflow row.
- **Programmatic HTTP e2e (Upsert Document body — synthetic graph + `/run`)** — From `backend/`, `uv run python scripts/run_upsert_document_http_e2e.py` starts a temporary **uvicorn**, logs in (`POST …/auth/login`), **creates** workflows (**`POST …/workflow-definitions/`**) with toy graphs (String primitive → **Upsert Document**: **`target_handle: "name"`** mis-wire + explicit **`content`** + alias **`output`**), **`POST …/workflow-definitions/{id}/run`**, and asserts **`GET …/documents/{id}`** **`body`** matches the wired text. No LM; no outbound network. For **persisted** definitions exercised like the SPA (**`POST …/runs`** + SSE), see **`run_persisted_workflow_stream_http_e2e.py`** above instead.
- **Optional pytest (Image primitive + real LM Studio)** — `cd backend && RUN_IMAGE_E2E=1 uv run pytest tests/test_image_primitive_workflow_e2e_optional.py -v` runs a small **Image** → **Multimodal LLM** graph with an **unmocked** LM Studio client. Skips unless **`RUN_IMAGE_E2E=1`** and **`GET {LMSTUDIO_BASE_URL}/models`** succeeds (same base URL as other local LLM tooling). Requires a **vision-capable** model for the chosen Persona.

### Script run succeeds, editor **Run** fails (or `ERR_INCOMPLETE_CHUNKED_ENCODING`)

The script always uses **your** local API process and **`backend/.env`**. The SPA calls **`POST …/runs`** and opens **`GET …/workflow-runs/{id}/events`** on **`API_BASE`** ([`frontend/src/api/baseUrl.ts`](../frontend/src/api/baseUrl.ts): **`VITE_API_BASE`** at build time, or dev inference from **`window.location`**). If those differ, you are not comparing the same backend:

1. **Hosted API vs home LM Studio** — A browser pointed at **`https://api.example.com`** runs the workflow on the **server**. That host must have a reachable **`LMSTUDIO_BASE_URL`** (LM on the same VPS, tunnel, etc.). Your **laptop’s** LM Studio at **`127.0.0.1`** or **`10.x.x.x`** is **not** reachable from a cloud API. The **offline script on your Mac** *can* reach it. **Fix:** For local LM dev, run the SPA against **`http://127.0.0.1:8000`** (set **`VITE_API_BASE`** in `frontend/.env` and restart Vite) and run **`uvicorn`** locally with the same **`backend/.env`** as the script.

2. **Reverse proxy / nginx** — Long **`GET …/workflow-runs/…/events`** (**SSE**) or **Workspace** **`…/turns/stream`** / **`confirm-stream`** responses can show **`net::ERR_INCOMPLETE_CHUNKED_ENCODING`** if the proxy **buffers**, **times out**, or **closes** the stream early. The run may still finish on the server while the **browser** loses the stream. **CORS preflight (`OPTIONS`)** is **short** and may **200** before the **`GET`** that holds **`text/event-stream`** open. **Fix:** Use **`proxy_buffering off`**, **`proxy_read_timeout`** (e.g. 3600s), and **`X-Accel-Buffering: no`** on the SSE location; reload nginx; or call the API on **`localhost:8000`** to confirm. See [DEPLOYMENT_AND_NETWORK.md](DEPLOYMENT_AND_NETWORK.md) and [examples/nginx/mind-weave.conf.example](examples/nginx/mind-weave.conf.example).

3. **React Flow handle warnings** — Warnings like **#008** during a **live run** are usually **cosmetic**; they do not change **`WorkflowExecutor`** behavior. Prefer **Network** tab + the **`events`** (**SSE**) response over canvas noise when debugging. **Editor load** warnings for missing handles were either a **load-timing race** (fixed by deferred edge commit; see **Workflow run history** / canvas fit in [ARCHITECTURE.md](ARCHITECTURE.md)) or **bad persisted wiring** (e.g. **`source_handle`** no longer on **Start**). For fixable wiring problems, open **Run Logs** or **Explorer → Graph issues** (nothing selected) or run **`analyze_workflow_definition.py --workflow-id <uuid> --wiring-issues`** (see [Debugging workflows](#debugging-workflows-graphs-and-runs)).

### Manage Documents shows empty Body after an Upsert run

If a workflow ran an **Upsert Document** step, the document appears in **Manage Documents** with the right **Name**, **Description** is empty (expected), but the **Body** textarea is empty:

1. **Confirm persistence is fine before suspecting the executor.** From `backend/`, run **`uv run python scripts/run_persisted_workflow_stream_http_e2e.py --workflow-id <uuid> --assert-upsert-body-non-empty`** (use credentials of the **owning user**). Exit **0** means the streamed run’s Upsert **`output.markdown`** is non-empty **and** **`GET /api/v1/documents/{id}`** **`body`** matches it. Pair with **`uv run python scripts/analyze_workflow_definition.py --workflow-id <same-uuid> --summarize`** to inspect the **target_handle** wiring into the upsert node (**`name`** mis-wire, alias **`output`/`text`/`body`/`markdown`**, etc.).
2. **If step 1 exits 0 but the SPA still shows an empty Body, it is a UI hydration bug**, not a persistence regression. The list endpoint **`GET /api/v1/documents/`** returns **`DocumentListItem`** which intentionally **omits `body`** (see *Slim list schemas* in [ARCHITECTURE.md](ARCHITECTURE.md) and [`backend/app/domain/schemas/documents.py`](../backend/app/domain/schemas/documents.py)). Detail editors must call **`GET /api/v1/documents/{id}`** when a row gains focus and hydrate the textarea from that response. The canonical fix lives in [`DocumentManager.tsx`](../frontend/src/components/DocumentManager.tsx) (`hydrateFocusBody`, with a focus-token ref to discard stale responses). **Rebuild / hard-refresh the SPA** after pulling the fix; in the **Network** tab opening a row should fire **`GET /api/v1/documents/{id}`** before the Body field populates.
3. **If step 1 exits non-zero**, treat it as a real persistence problem and follow the **Programmatic HTTP e2e (Upsert Document body)** runner output for which **target_handle** alias / mis-wire path failed; if needed cross-check the row directly: **`sqlite3 backend/mindweave.db "SELECT name, length(body) FROM documents WHERE id='<uuid>';"`** vs the script's reported markdown length.

## Text-to-Speech (TTS bridge)

- **Process** — Run [`services/tts-bridge`](../services/tts-bridge/README.md) on the same host that holds GPU / model weights (default **`http://127.0.0.1:8765`**). Point Mind Weave at it with **`TTS_BRIDGE_URL`**; optional **`TTS_BRIDGE_TOKEN`** must match header **`X-TTS-Bridge-Token`** on the bridge when set. If synthesis fails with errors that sound like an **old** bridge build (e.g. meta-tensor) after you upgraded, confirm nothing else is already listening on the bridge port (**`lsof -i :8765`**) and restart the correct process — you may have been hitting a **stale** listener. **`GET /health`** includes **`qwen_torch_cache_revision`**; it must change when the bridge load code changes.
- **Mind Weave env** — **`TTS_BRIDGE_PULL_TIMEOUT`**, **`TTS_BRIDGE_SYNTH_TIMEOUT`**, **`TTS_BRIDGE_MAX_AUDIO_BYTES`** (see [`backend/app/core/config.py`](../backend/app/core/config.py)). Weights directory: **`TTS_MODEL_ROOT`** on the bridge; keep **`.local/`** gitignored (see repo **`.gitignore`**).
- **Registry** — Admins add models under **My Settings → TTS models** (downloads can take a long time and use large disk). All users can select **`ready`** models in the workflow editor. **`qwen_mlx`** may return **501** until implemented; use **`qwen_torch`** with **`TTS_BRIDGE_MOCK=1`** for smoke tests without weights.
- **Voice Design vs clone checkpoints** — **Voice Design** models support text-only TTS. **Base** (voice clone) checkpoints require **reference audio** (workflow **voice sample** or **`ref_audio_base64` + `ref_text`** in node options) — the bridge will not run **`generate_voice_design`** on a Base model. In practice operators register both: a Design model for **Voice samples → preview design** and a Base model for runs that set **`voice_sample_id`**.
- **Voice samples API** — Authenticated **`/api/v1/voice-samples`** CRUD is user-scoped. Reference audio size is capped consistently with **`TTS_BRIDGE_MAX_AUDIO_BYTES`**. **`preview-design`** triggers GPU synthesis on the bridge like workflow TTS; treat it as expensive and avoid abuse (same host constraints as the bridge).
- **Reverse proxy body limit** — **`POST /api/v1/voice-samples/`** carries **base64** audio in JSON, and runtime **Audio File Input** can upload multipart audio up to the STT cap. If **nginx** (or another proxy) uses the default **`client_max_body_size`** (**1m**), the proxy returns **413** before FastAPI runs. That error page usually **omits CORS headers**, so the SPA shows a **CORS** or **Failed to fetch** error instead of a clear size message. Set **`client_max_body_size`** above the app cap, e.g. **100m** for the default **75 MiB** STT upload cap (see [examples/nginx/mind-weave.conf.example](examples/nginx/mind-weave.conf.example)).
- **Voice clone / “File name too long”** — If workflow TTS with a **voice sample** failed with **`[Errno 63] File name too long`** and a huge “path” of base64, the TTS bridge was passing raw **`ref_audio_base64`** into **`qwen_tts`**, which mis-classifies strings containing **`/`** as paths. **Redeploy** a bridge build that decodes base64 to **`(waveform, sr)`** before **`generate_voice_clone`** (see [`services/tts-bridge/tts_bridge/engines/qwen_torch.py`](../services/tts-bridge/tts_bridge/engines/qwen_torch.py)).
- **Bridge `unsupported scalarType` (500)** — Usually PyTorch **MPS** dtype / dispatch mismatch. The bridge uses **float32** on MPS. If you still see this error, set **`TTS_BRIDGE_DEVICE=cpu`** on the bridge host and retry; see [`services/tts-bridge/docs/APPLE_SILICON.md`](../services/tts-bridge/docs/APPLE_SILICON.md).
- **Bridge “Cannot copy out of meta tensor” / `to_empty()` (HTTP 500 on `/v1/tts`)** — PyTorch uses **`NotImplementedError`** for invalid copies from the **meta** device; older bridge builds mapped **every** `NotImplementedError` to **501**, which looked like an unimplemented *engine* even when **`qwen_torch`** was in use. Current builds return **500** for meta-tensor / `to_empty()` messages. Underlying cause: the **`qwen-tts`** stack loads **`speech_tokenizer`** from **`\<model\>/speech_tokenizer`** after the main model; the inner **`AutoModel`** can end up on **meta** if kwargs do not match the main load, and **`Qwen3TTSTokenizer`** is not an **`nn.Module`**, so it is **not** moved by the parent’s **`.to(device)`** until the bridge does so explicitly. The bridge **re-loads** that tokenizer with **`torch_dtype`**, **`low_cpu_mem_usage=False`**, **`device_map=None`**, then **moves the inner `speech_tokenizer.model`**. **After upgrading the bridge, restart the tts-bridge process** (workers cache the loaded model; the cache key includes a **revision** token so deploys do not keep stale bad loads). If problems persist, set **`TTS_BRIDGE_DEVICE=cpu`**. See [`qwen_torch.py`](../services/tts-bridge/tts_bridge/engines/qwen_torch.py) and [`services/tts-bridge/docs/APPLE_SILICON.md`](../services/tts-bridge/docs/APPLE_SILICON.md). **True** “not implemented” engines (e.g. **`qwen_mlx`**) still return **501**.
- **Stored blobs** — Saved samples keep WAV bytes in the app DB; plan capacity and backups accordingly.

## Speech-to-text (STT bridge)

- **Process** — Run [`services/stt-bridge`](../services/stt-bridge/README.md) on a host with **`faster-whisper`** (default bind **`http://127.0.0.1:8766`**). Point Mind Weave at it with **`STT_BRIDGE_URL`**; optional **`STT_BRIDGE_TOKEN`** must match header **`X-STT-Bridge-Token`** on the bridge when set. Use **`STT_BRIDGE_MOCK=1`** on the bridge for CI-style smoke tests without model weights. Downloaded model weights are kept **out of git** (see service **`.gitignore`** / **`README`**).
- **Mind Weave env** — **`STT_BRIDGE_URL`**, **`STT_BRIDGE_TOKEN`**, **`STT_BRIDGE_TIMEOUT`**, **`STT_AUDIO_WAIT_TIMEOUT`** (how long a **`transcribe_audio`** step waits for a browser upload after **`input_required`**), **`STT_MAX_AUDIO_UPLOAD_BYTES`** (max multipart size for the resume route and the bridge) — see [`backend/app/core/config.py`](../backend/app/core/config.py).
- **Editor contract** — Workflow **Voice input** is **not** an always-on listener: the client records while the run is in **`input_required`**, then uploads. **Audio File Input** uses the same pending handoff when no saved audio artifact is configured; when `audio_artifact_id` is set, the API reads the saved user-owned file directly. If you operate multiple API workers, the in-process pending map does not cross processes (use a single worker locally or plan for shared state later).
- **Runtime Audio File Input troubleshooting** — A selected file first uploads to **`POST /api/v1/workflow-runs/{run_id}/audio-file-input`**, then the API calls the STT bridge. Runtime files are capped at **`STT_MAX_AUDIO_UPLOAD_BYTES`** (**75 MiB** by default); the editor uses **`VITE_STT_MAX_AUDIO_UPLOAD_BYTES`** (same default) to reject larger files before upload because reverse proxies often drop oversized multipart bodies before FastAPI can return JSON. A browser **`Failed to fetch`** at the file picker means the upload request itself failed at the network/proxy/CORS layer; check the backend process, `VITE_API_BASE`, reverse-proxy `client_max_body_size`, and CORS headers before debugging the STT bridge. A completed upload followed by a workflow step error such as **`Transcription failed: ...`** means the upload handoff worked and the bridge request failed. Stream disconnects now mark the run **`error`** and clear pending waits instead of leaving the row indefinitely **`running`**.
- **Audio file artifacts** — **`/api/v1/audio-file-artifacts`** stores uploaded audio bytes in the app database for reuse by **Audio File Input**. Supported V1 extensions are **mp3**, **wav**, **m4a**, **ogg**, **flac**, and **webm**; uploads are capped by **`STT_MAX_AUDIO_UPLOAD_BYTES`**. Plan DB capacity and backups accordingly.
- **Debug API** — Authenticated **`POST /api/v1/stt/transcribe`** (multipart) proxies to the same bridge; useful for manual checks without a workflow run.

### Speech transcription providers (`transcribe_file`)

The provider-abstracted **`transcribe_file`** skill is additive to **Voice input** and **Audio File Input** above and is gated separately from the legacy STT bridge skills.

- **Allow-list** — **`TRANSCRIPTION_PROVIDERS_ENABLED`** in [`config.py`](../backend/app/core/config.py) controls which providers the editor advertises through **`GET /api/v1/transcription/providers`**. Default includes **`local_whisper`** and **`assemblyai`**. Set to **`["local_whisper"]`** only if the operator wants to hide the cloud option from authors.
- **Local Whisper** — Uses the same **`services/stt-bridge`** as `transcribe_audio` / `audio_file_input`. No additional config; the same env table above applies. Audio never leaves your server.
- **AssemblyAI** — Cloud STT. Per-user API keys live under **My Settings → API Settings** (key name `assemblyai`); they are encrypted at rest (`user_api_keys_crypto`). Server-wide fallback **`ASSEMBLYAI_API_KEY`** is consulted only when the user has no personal key. Create-transcript requests send **`speech_models`** (default **`["universal-3-pro"]`**, configurable via **`ASSEMBLYAI_SPEECH_MODELS`**). Tunables: **`ASSEMBLYAI_BASE_URL`** (default `https://api.assemblyai.com`), **`ASSEMBLYAI_UPLOAD_TIMEOUT`**, **`ASSEMBLYAI_REQUEST_TIMEOUT`**, **`ASSEMBLYAI_POLL_INTERVAL`** (inline poll cadence while a stream is attached), **`ASSEMBLYAI_JOB_TIMEOUT`** (total inline budget before the executor falls back to the lifespan poller). See [DEPLOYMENT_AND_NETWORK.md](DEPLOYMENT_AND_NETWORK.md) for the outbound HTTPS allow-list this requires.
- **Persisted async jobs** — `transcription_jobs` rows are written **before** the provider call so a process crash mid-submit leaves a recoverable breadcrumb. The lifespan poller defined in [`transcription_job_poller.py`](../backend/app/domain/services/transcription_job_poller.py) ticks every **`TRANSCRIPTION_JOB_POLL_INTERVAL`** seconds (default 5; set to 0 to disable). It only advances rows for **non-synchronous** providers — `local_whisper` rows always finalize inline and are skipped. Multi-worker deployments need a shared lock to avoid duplicate polling (same caveat as `transcribe_pending`); the V1 expectation is single-worker.
- **Reconnect / replay** — **`GET /api/v1/workflow-runs/{run_id}/events`** (**SSE**) **replays** persisted node logs + `transcription_jobs` deltas, then **tails** live until the workflow run is terminal. Idempotent reopen; safe after a reload, network blip, or API restart (**`Last-Event-ID`** resume not required for v1; full replay rebuilds canvas state).
- **Transient artifacts** — Runtime uploads (no `audio_artifact_id`) to non-synchronous providers spill bytes into a `transient=true` `audio_file_artifacts` row so the poller can re-read them. Transient rows are **hidden** from `GET /audio-file-artifacts/` and are deleted automatically when the job reaches a terminal status.
- **Programmatic e2e** — `cd backend && uv run python scripts/run_transcribe_file_workflow_e2e.py` (in-process; mocks STT and AssemblyAI by default; `--real-stt` / `--real-assemblyai --assemblyai-key …` switches to live calls). The HTTP twin `scripts/run_transcribe_file_workflow_http_e2e.py` boots a local FastAPI process, exercises **`POST …/runs`** + **`GET …/events`**, and verifies replay/tail (**AssemblyAI**) matches persisted **`transcription_jobs`** state.

## Local LLM timeouts (Simple LLM Call / LM Studio)

**LM Studio host** — Only **`LMSTUDIO_BASE_URL`** in server config (`.env`); the browser never talks to LM Studio directly. **Authentication** — **`Authorization: Bearer`** is sent on every LM Studio request. **Model pickers** (`GET /api/v1/models/`) call LM Studio with **`LMSTUDIO_API_KEY`** only so all users share the same model id list. **Chat and workflow LLM steps** still prefer per-user **`lmstudio_api_key`** in **My Settings → API**, then fall back to **`LMSTUDIO_API_KEY`**. If there is no user key and no env key, Simple LLM steps fail with a clear error; if **`LMSTUDIO_API_KEY`** is unset, pickers return an empty **`local`** list and **`lm_studio_list_error`** explains why.

**401 from LM Studio** — Usually wrong or missing API key. Re-enter **`lmstudio_api_key`** in My Settings (or set **`LMSTUDIO_API_KEY`** on the server). Saving API settings after loading the page without retyping used to persist the masked **`[stored]`** placeholder; that is now ignored on save—if you still see **401**, save a fresh key once or set the env fallback.

**400 from LM Studio** — Two distinct failure modes; the backend handles them differently:

1. **Cold-start warmup race.** When a parallel **For Loop** (`parallel_iterations: true`) fans several Simple LLM Calls into a just-loaded model, the *first* request sometimes arrives during the window where native **`GET /api/v1/models`** already reports **`loaded_instances`** but the OpenAI runtime (`/v1/chat/completions`) is still warming up. LM Studio returns **400** with a body like **`{"error":"Model not loaded"}`**, **`"No runtime is loaded"`**, **`"Model is warming up"`**, or **`"Still loading"`**. [`_post_chat_completions`](../backend/app/providers/lmstudio.py) detects these warmup-shaped 400s (case-insensitive markers: **`model not loaded`**, **`no runtime`**, **`model is loading`**, **`model is warming`**, **`warming up`**, **`not ready`**, **`still loading`**) and retries them inside **`LMSTUDIO_CHAT_RETRY_BUDGET_SECONDS`** (same budget and exponential backoff used for **500/503/504**). Subsequent iterations reuse the warm model and incur no retry.
2. **Real request errors** — unknown model id, **`response_format.json_schema.schema`** rejected by the MLX/outlines backend, prompt exceeds context length, etc. These are **not** retried; instead the provider now raises **`ValueError("LM Studio returned 400 Bad Request: <body>")`** so the Simple LLM Call step error (and **Last Run** / **Run Logs**) shows the actual LM Studio message (parsed from `error` / `error.message` / `message` when the body is JSON, else raw text capped at 2 KiB). Previously the step only showed **`HTTPStatusError: Client error '400 Bad Request' for url '...' For more information check: https://developer.mozilla.org/...`** — the body was discarded.

**Simple LLM Call** chat requests use **`LMSTUDIO_CHAT_TIMEOUT`** (seconds). Default is **3600** (1 hour) for large/slow local models and heavy structured outputs. Override in `.env` or deployment env; see the env table in [backend/README.md](../backend/README.md#environment-variables).

**Usage payload shape** — **`POST …/v1/chat/completions`** responses may include nested **`usage`** objects (e.g. per-model token breakdowns). The backend flattens these to integer fields before building `ProviderResponse`; flat `usage` from older stacks is unchanged.

**Reasoning / thinking (Persona)** — LM Studio **0.4.8+** documents **`reasoning_effort`** and **`reasoning_tokens`** on the OpenAI-compatible **`v1/chat/completions`** request body. When a **Persona** has **`suppress_lm_thinking`** enabled (**Manage Personas**), Mind Weave adds **`reasoning_effort: "none"`** to matching requests (workspace pipeline stages tied to that Companion’s Persona, and **Simple LLM Call** steps using that Persona). Older LM Studio builds or models that ignore the field behave as before.

**Model load (JIT)** — **Simple LLM Call** workflow steps use LM Studio’s OpenAI-compatible **`POST …/v1/chat/completions`** endpoint (same HTTP API whether you call it from a workflow or elsewhere). Before that request, the backend may call LM Studio’s native **`GET /api/v1/models`** and **`POST /api/v1/models/load`** so an unloaded model is loaded once under a per-model lock (parallel waves no longer all fail until load finishes). **`LMSTUDIO_MODEL_LOAD_TIMEOUT`** caps how long a load may block. After **`POST …/load`** returns, LM Studio may still be initializing the GPU context; the backend then **polls** native **`GET /api/v1/models`** until the model shows **`loaded_instances`** (or **`LMSTUDIO_MODEL_READY_MAX_WAIT_SECONDS`** elapses; **`0`** disables polling — see env table in [backend/README.md](../backend/README.md#environment-variables)). The **completions** request also **retries** transient errors including **500** (common while the model is not ready yet), **503**, **502**, **429**, and **504**, within **`LMSTUDIO_CHAT_RETRY_BUDGET_SECONDS`** (env name reflects LM Studio / OpenAI route naming).

**`GET /models/` timeout** — The model-list endpoint uses a **2-second** timeout to LM Studio (local service; should respond quickly). If LM Studio is slow or down, **`local`** is empty and **`lm_studio_list_error`** may be set (response stays **200** so the UI can render); server logs still record failures.

**Proxies (`HTTP_PROXY` / `HTTPS_PROXY`)** — LM Studio requests use **`httpx.AsyncClient(trust_env=False)`** in [`lmstudio.py`](../backend/app/providers/lmstudio.py) and the **`GET .../models`** handler in [`models.py`](../backend/app/api/v1/models.py). That way IDE or agent environments that set a global HTTP proxy do not send **`http://127.0.0.1:…`** or LAN LM URLs through the proxy (which often fails with **ConnectError** while **`uvicorn`** started from a clean terminal still works).

**Build run SSE keepalive (~25s)** — While a **parallel batch** (e.g. several Simple LLM nodes) runs, **`GET …/workflow-runs/{id}/events`** may emit **SSE comment** lines (and inline keepalive-shaped **`data:`** events) so **nginx** (`proxy_read_timeout`) and **home-router port-forward NAT** (often **~60s** idle) see traffic before the next **`node.completed`**. The editor ignores comment lines and unknown event kinds for run phase state.

**Workspace SSE keepalive (~25s)** — **`POST …/workspaces/…/turns/stream`** and **`…/confirm-stream`** may sit in **interpret**, **capability execution**, or **compose** LM calls for a long time with **no token chunks** yet. The runtime emits **SSE comment** lines (`: sse-keepalive`) on the same interval so proxies see traffic (same motivation as **Build** **`…/events`**). Browsers ignore comment lines; the Workspace SPA only parses `data:` JSON events.

**Parallel batch size** — Each wave runs at most **`User.settings.max_concurrent_lm_studio_calls`** ready steps at once (default **3**, max **32**), including non-LLM steps that happen to become ready in the same wave. Users change it under **My Settings → System Settings** (label: **Max concurrent LM Studio calls**) to reduce LM Studio load when many branches fan out in parallel. Server-side caps also include **`WORKFLOW_MAX_CONCURRENT_NODES`**, **`WORKFLOW_MAX_CONCURRENT_LLM_CALLS`**, **`WORKFLOW_MAX_CONCURRENT_BROWSER_TASKS`**, **`WORKFLOW_MAX_CONCURRENT_EXTERNAL_SKILL_TASKS`**, and **`WORKFLOW_MAX_CONCURRENT_TTS_TASKS`** (dedicated slot for **text_to_speech**; see [`config.py`](../backend/app/core/config.py)).

**Session vs parallel waves** — Ready nodes in a wave run concurrently (`asyncio.gather`). The executor uses **one** SQLAlchemy **`Session`** per request; concurrent tasks must **not** call into that session unsynchronized. Token resolution and other ORM reads for **Simple LLM Call** run under an internal async lock; **outbound** LM Studio HTTP runs outside it. If you add a new step that hits the DB from parallel nodes, follow the same pattern (brief locked ORM, then I/O outside). Misuse can cause intermittent auth or bad reads even when the DB and [`inspect_user_lmstudio_key.py`](../backend/scripts/inspect_user_lmstudio_key.py) look correct. Architecture: [ARCHITECTURE.md](ARCHITECTURE.md) (workflow executor Session concurrency).

## Performance profiling

### Request timing middleware

[`RequestTimingMiddleware`](../backend/app/main.py) logs every HTTP request to the **`mindweave.perf`** logger: `METHOD /path STATUS DURATIONms`. Each response also includes a **`Server-Timing: total;dur=<ms>`** header visible in browser DevTools (Network tab → select a request → Timing).

Startup lifespan phases (migrations, seed + purge, total) are logged to the same logger with their own timing labels, so operators can see exactly how long each phase takes on a cold start.

### API timing script

[`backend/scripts/measure-api-timing.sh`](../backend/scripts/measure-api-timing.sh) uses `curl` to hit key endpoints and report DNS, TCP, TLS, TTFB, and total transfer time for each.

```bash
cd backend
./scripts/measure-api-timing.sh                                    # default: http://localhost:8000/api/v1
./scripts/measure-api-timing.sh http://localhost:8000/api/v1 --cookie cookies.txt  # authenticated
```

Endpoints tested: `/health`, `/auth/me`, `/workspaces/bootstrap`, `/models/`, `/personas/`, `/documents/`, `/palettes/`, `/workflow-definitions/`. The script reports timing for each in a columnar format.

### Frontend performance marks

In development mode, the SPA records `performance.mark()` entries at key milestones: `mw:main-start`, `mw:imports-done`, `mw:render-called`, `mw:auth-check-start`, `mw:auth-check-done`, `mw:app-render`, `mw:workspace-bootstrap-start`, `mw:workspace-bootstrap-done`. After 3 seconds, a grouped console log shows each mark with its offset from `mw:main-start` (open DevTools Console to see it).
