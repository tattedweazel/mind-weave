# Workspace (Companion chat runtime)

Operational reference for the **Workspace** feature: a staged conversational runtime with a persistent **Companion**, **workflow definitions** as invocable capabilities, streaming delivery, and **Workspace Replay** observability.

Product background and contracts live in the repo-root draft [`mind_weave_companion_workspace_spec.md`](../mind_weave_companion_workspace_spec.md). **This file is the implementer SSOT** for APIs, configuration, and behavior.

## Architecture

| Layer | Owns |
| ----- | ---- |
| **Domain** | Turn contracts ([`backend/app/domain/schemas/workspace_contracts.py`](../backend/app/domain/schemas/workspace_contracts.py)), `CapabilitySpec` ([`backend/app/domain/workspace/capabilities.py`](../backend/app/domain/workspace/capabilities.py)), resolution of `wf:{uuid}` keys ([`backend/app/domain/workspace/capability_resolution.py`](../backend/app/domain/workspace/capability_resolution.py)), Start-slot metadata for prompts ([`backend/app/domain/workspace/start_inputs.py`](../backend/app/domain/workspace/start_inputs.py)), runtime orchestration ([`backend/app/domain/services/workspace_runtime_service.py`](../backend/app/domain/services/workspace_runtime_service.py)) |
| **Persistence** | `companions`, `workspaces`, `workspace_sessions`, `workspace_turns`, `workspace_replays`, `companion_memory_entries` ([`backend/app/persistence/tables.py`](../backend/app/persistence/tables.py)); Workspace stores **`enabled_workflow_ids`**, optional **`interpretation_model`**; Companion stores **`enabled_workflow_ids`** |
| **HTTP** | [`backend/app/api/v1/companion_api.py`](../backend/app/api/v1/companion_api.py), [`backend/app/api/v1/workspaces_api.py`](../backend/app/api/v1/workspaces_api.py) — thin routes → services; workflow allow-lists validated against [`WorkflowDefinitionService`](../backend/app/domain/services/workflow_definition_service.py) |

## Language model (LM Studio)

Workspace uses **two** chat-completion roles:

| Stage | Model selection |
| ----- | ---------------- |
| **Interpret** (structured JSON: capabilities + Start `input_bindings`) | Optional **`runtime_configuration.companion_pipeline.stages.interpret.model_override`** when that stage is enabled. Else **`workspaces.interpretation_model`** when set. Else **Persona `default_model`** → **`LMSTUDIO_MODEL`** → first id from **`GET …/v1/models`**. |
| **Process** (optional LLM steps between execute and compose) | Per-step **`model`** on each **`process`** entry when set; else same resolution as **Compose**. |
| **Compose** (user-visible reply text; Persona **system prompt** is the default **voice**) | Optional **`companion_pipeline.stages.compose.model_override`** when enabled. Else **Persona `default_model`** → env → auto-pick. **Voice** may be overridden by **`companion_pipeline.stages.compose.voice_override`** (non-empty string). When process steps are configured and produce output, compose receives processed outputs instead of raw capability data and acts as a coherence step. |
| **Session summary** (rolling **`active_summary`**) | Optional **`companion_pipeline.stages.session_summary.model_override`** when enabled. Else **`session_summary_model`** on **`runtime_configuration`**, then **`interpretation_model`**, then Persona default (unchanged chain). |
| **Post-compose** (optional LLM steps after compose) | Per-step **`model`** on each **`post_compose`** entry when set; else same resolution as **Compose**. |

**Persona: suppress extended thinking** — In **Manage Personas**, a Persona can opt in to **`suppress_lm_thinking`**. When enabled, workspace LM calls that use that Companion’s Persona (interpret, compose, session summary, process/post-compose steps, etc.) include **`reasoning_effort: "none"`** on **`POST …/v1/chat/completions`** (LM Studio **0.4.8+**). Default is off so thinking-capable models keep server defaults. Workflow **Simple LLM Call** steps honor the same flag via the selected Persona.

The historical placeholder **`local-model`** is **not** sent to LM Studio; it triggers auto-pick from **`GET …/v1/models`**. Ensure LM Studio is running. **Persona/workspace model dropdowns** use **`LMSTUDIO_API_KEY`** on the server for that list; **chat** still uses **My Settings → LM Studio API key** first, then env.

## Google workflow skills and identity

Capability runs use **`WorkflowExecutor(session, current_user.id, …)`** — the **authenticated user**, not a separate Companion principal. Gmail, Calendar, and Google Docs skills resolve OAuth from the user’s single workflow Google account ([`get_user_workflow_google_connection`](../backend/app/integrations/google_workflow_connection.py)) linked under **My Settings → Google Account → Google for workflows**. Legacy **`google_connection_id`** values stored on skill nodes in saved graphs are **ignored** at run time. Tokens are loaded with [`ensure_workflow_google_access_token`](../backend/app/integrations/google_workspace.py), which requires the connection row’s **`user_id`** to match the run’s user.

### Troubleshooting (Companion / Workspace runs)

| Symptom | Things to check |
| ------- | ---------------- |
| **Google workflow connection required** | Connect or re-connect under **My Settings → Google Account → Google for workflows**; failing node is **Gmail List Messages**, **Calendar List Events**, or **Google Docs Get Document**. Re-connecting refreshes scopes without updating individual workflows. |
| **Start input missing (e.g. `email_list`)** | Interpreter must use **exact** keys from the capability line (e.g. `email_list`, not `emailList`). Use JSON arrays for `list` slots. If a **Gmail List Messages** skill exists on the **top-level graph or (depth-limited) nested refs** and the Start node defines a required **`email_list`** slot **without a graph default** (any declared slot type), the runtime supplies **`[]`** when the interpreter omits the key; validation accepts that array even if the slot was mis-typed as `gmail` in the graph. |
| **Confirm returns HTTP 400** | **`confirm-stream`** rejects confirmation when required Start inputs are still missing or have the wrong JSON shape, even if the UI allowed opening Confirm. Cancel the proposal and rephrase so the interpreter supplies bindings. |
| **Same workflow twice in one turn** | **`selected_capabilities`** is a list: two entries with the same **`wf:{uuid}`** can run **twice** with **different** `input_bindings` (e.g. unread vs all). Execution uses each row’s bindings in order. |

## HTTP API (authenticated)

Base path: `/api/v1`.

| Method | Path | Purpose |
| ------ | ---- | ------- |
| `GET` | `/companion/` | Current user’s Companion (lazy-created). |
| `PUT` | `/companion/` | Update Companion fields (`enabled_workflow_ids` must reference workflows the user can access). |
| `GET` | `/companion/memory` | List memory entries (optional `approval_status` query). |
| `POST` | `/companion/memory/{id}/decision` | Body `{ "decision": "approved" \| "rejected" }` for **proposed** entries. |
| `POST` | `/workspaces/bootstrap` | Ensure default **Companion Chat** workspace + session. Returns the **most recently updated** session for that workspace (`updated_at` desc), not necessarily an empty thread. |
| `GET` | `/workspaces/` | List workspaces. |
| `POST` | `/workspaces/` | Create workspace. |
| `GET` | `/workspaces/{id}` | Get workspace. |
| `PUT` | `/workspaces/{id}` | Update workspace: `enabled_workflow_ids` (UUID strings), optional `interpretation_model`. |
| `GET` | `/workspaces/{id}/sessions` | List sessions. |
| `POST` | `/workspaces/{id}/sessions` | Create session (`title` optional). |
| `GET` | `/workspaces/{id}/sessions/{sid}/turns` | List turns (metadata). |
| `GET` | `/workspaces/{id}/sessions/{sid}/turns/{tid}` | Single turn with **redacted** `traces` for the Workspace Console. Stages other than execution use the same redaction as replay storage. **`execution_results`** returns a **sanitized summary** only: per-capability `status`, `error`, and `validation` (no workflow outputs), so failed node messages stay visible without leaking email bodies or other skill payloads. |
| `GET` | `/workspaces/{id}/pipeline/preview` | **No LLM calls.** Returns merged **system** strings and resolved **models** for interpret, compose, session-summary, and each **post-compose** step (for the Pipeline settings UI). |
| `POST` | `/workspaces/{id}/sessions/{sid}/turns/stream` | Body `{ "message": "..." }` — **SSE** (`text/event-stream`): token chunks, optional `capability_proposal` event, then `done` (see below). |
| `POST` | `/workspaces/{id}/sessions/{sid}/turns/confirm-stream` | Body `{ "proposal_id": "...", "cancel": true \| false }` — **SSE** after validation: if `cancel` is `false` and required Start inputs are missing or malformed, responds **400** (no stream). Otherwise streams the follow-up assistant text after confirming, or a short cancel acknowledgment when `cancel` is `true`. |
| `GET` | `/workflow-definitions/` | List workflow definitions for the allow-list UI (slim response without `graph`; use `GET .../{ id }` for the full definition). |

**SSE events (stream and confirm-stream)**

- `data: {"event":"token","text":"..."}` — partial assistant text.
- `data: {"event":"stage","stage":"interpret"|"compose"|"execute"|"process:{id}"|"session_summary"|"post_compose:{id}","status":"started"|"completed","ms"?:number,"detail"?:object}` — lifecycle markers for pipeline stages (confirm-stream includes **`execute`** and **`process:{id}`** when process steps are configured). **`ms`** is set on **`completed`** when measured server-side.
- `data: {"event":"capability_proposal","proposal_id":"...","capabilities":[...]}` — emitted when the interpreter selected allowed workflows; each capability includes `capability_key`, workflow `name`, `input_bindings`, plus **`start_slots`** and **`missing_start_binding_keys`** when the graph defines Start inputs. The client must call **confirm-stream** to run or cancel; no **WorkspaceTurn** is written until then.
- `data: {"event":"done",...}` — `phase` is `"proposal"` (awaiting confirm), `"completed"` (turn persisted), or `"cancelled"` (proposal cleared, no turn). Completed turns include `turn_id`, `replay_id`, and `memory_proposed` as before.

During long **interpret**, **capability execution**, or **compose** LM calls, the server may emit **SSE comment** lines (`: sse-keepalive`, ~every 25s) so reverse proxies and NAT do not treat the stream as idle (~60s) and close it. The SPA only parses `data:` lines; comments are ignored.

Rate limit: `POST .../turns/stream` and `POST .../turns/confirm-stream` each use the same **`WORKFLOW_RUN_RATE_LIMIT`** per-IP budget as workflow runs (see [`build_workspace_turn_stream_rate_limit_rules`](../backend/app/core/auth_rate_limit.py)).

## Runtime (V1)

1. **Interpret** — LM Studio structured JSON → `InterpretationPayload` (fallback to direct reply on failure). When **`workspace_sessions.active_summary`** is non-empty, a bounded **session memory** block is appended to the **system** prompt (compressed prior turns; not treated as new user instructions) so follow-ups like “what did I ask you to do?” can be resolved. On the first turn of a session that already has persisted **`WorkspaceTurn`** rows but an empty **`active_summary`** (e.g. legacy data), the server may **backfill** the summary from the most recent turns (see **`session_memory_backfill_turns`** below) before interpret runs. The system prompt also includes a **temporal context** block: current time in **UTC** and, when the user’s profile **`workflow_time_zone`** resolves to an IANA zone (same source as workflow Gmail/Calendar runs), current time in that zone—so phrases like “last 5 days” map to **RFC3339** Start bindings for the real calendar instead of a stale model guess. When the Workspace ∩ Companion allow-list is **non-empty** and not larger than an internal cap (~32 workflows), the response **JSON Schema** replaces generic `input_bindings` objects with a **`oneOf`**: one branch per allowed **`wf:{uuid}`**, each listing **required** Start keys (from the workflow graph, excluding slots with graph defaults) and typed properties so the model cannot omit required fields inside `input_bindings`. If there are no enabled capabilities or the list is too large, the generic Pydantic schema is used (same as before). The prompt lists allowed capabilities as **`wf:{workflow_uuid} — WorkflowName`** plus **Start input slots** (union of every **`kind: "start"`** node: `required_inputs` keys/types, or legacy single `user_input` / `text`). The model fills **`normalized_inputs`** and/or per-candidate **`input_bindings`** using JSON types that match the slot (`list` → JSON array, `gmail` / `dictionary` / `structure` → object, RFC3339 strings for `datetime`, etc.). Values are merged per selected capability (per-candidate bindings override `normalized_inputs` on key conflicts).
2. **Route** — Deterministic plan: `candidate_capabilities` filtered to the Workspace ∩ Companion allow-list; `SelectedCapability.input_bindings` carry merged parameters.
3. **Confirm (mandatory for capability runs)** — If at least one capability is selected, the server stores a proposal in **`workspace_sessions.transient_state.capability_proposal`** (TTL 15 minutes), streams a short assistant preface plus **`capability_proposal`**, and **does not** increment `turn_count` or write a **WorkspaceTurn** until the user calls **confirm-stream**. `cancel: true` clears the proposal and streams a brief acknowledgment. On confirm, allow-lists are re-checked; stale proposals, disabled workflows, **missing required Start inputs**, or **invalid binding shapes** return **400** before streaming.
4. **Execute** — After confirmation, each **selected** capability runs in list order via [`WorkflowExecutor.run`](../backend/app/domain/services/workflow_executor/__init__.py) (the same **`wf:`** may appear more than once with different bindings). **`input_overrides`** come from that row’s merged bindings (filtered to known Start keys when the graph defines slots). **Session memory and chat history are never passed into** **`input_overrides`**—workflows only see structured Start inputs from the interpreter. Nested **`workflow`** nodes run in a child executor for the same user. Google Gmail/Calendar/Docs skills use the user’s workflow Google account from My Settings. **`execution_time_zone`** is resolved like workflow runs from the user’s **`workflow_time_zone`** profile setting (and profile `"system"` semantics). Capability output prefers the **Stop** node’s payload when present; otherwise the last successful node output.
5. **Process (optional)** — When `companion_pipeline.process` contains enabled steps, each runs in order on the execution output before compose. Five step kinds are supported: **review** (iterative quality gate—loops up to `max_iterations` or until LLM approves), **critique** (one-shot notes/observations), **summarize** (condenses list data into a structured summary), **investigate** (answers provided `questions` from the data), and **analyze** (performs statistical/analytical observations). Each step receives a compact representation of capability execution results and a user-provided `description` of the desired output. Results are stored as `ProcessPayload` and forwarded to compose. SSE emits `process:{step.id}` started/completed events. When no process steps are configured, this stage is skipped entirely and compose receives raw execution output (backward compatible).
6. **Compose** — When **process steps ran** and produced output, compose receives the processed outputs instead of raw capability data and acts as a **coherence** step—merging multiple process step outputs into one unified reply. When no process steps ran, compose works as before: LM Studio turns capability results + user message into final chat text with the **session memory** snippet, **temporal context**, and each capability line with optional **`structured_output=`**. The model is instructed to **summarize that data in plain language** for successes and to surface specific errors when a capability fails. Optional **memory_candidates** are still **proposed** until the user approves.
7. **Deliver** — Final text is **chunk-streamed** (SSE); then persist **WorkspaceTurn** + **WorkspaceReplay** and session counters, clear any proposal from `transient_state`, and **refresh** **`workspace_sessions.active_summary`** by merging a compact digest of the turn (user message, assistant reply, capability keys, execution status—no full workflow payloads) into the prior summary via LM Studio (with a deterministic fallback if the call fails). **Proposal-only** turns (awaiting **confirm-stream**) do **not** update **`active_summary`** until a turn is **persisted** (typically after confirm).

**Session memory tuning** (optional keys on **`workspaces.runtime_configuration`**): **`session_memory_max_prompt_chars`** (default 6000) caps how much of **`active_summary`** is injected into interpret/compose prompts; **`session_memory_max_stored_chars`** (default 8000) caps the stored summary length; **`session_memory_backfill_turns`** (default 12, 1–50) limits how many recent turns are read when backfilling an empty summary; **`session_summary_model`** overrides the model used **only** for the summary-merge call when no pipeline override is set (otherwise **`interpretation_model`**, then the companion persona’s default model).

**Companion pipeline** (optional object **`runtime_configuration.companion_pipeline`**, validated on workspace create/update): **`version`** (int); **`stages.interpret`** / **`stages.compose`** / **`stages.session_summary`** each support **`enabled`**, optional **`model_override`**, and optional text append fields (**`system_instructions_append`** for interpret; **`instructions_append`** + optional **`voice_override`** for compose; **`instructions_append`** for session summary). The interpret stage also supports **`system_prompt_base`**: when set (non-empty string), it **replaces** the built-in default classifier prompt (`DEFAULT_INTERPRET_BASE_PROMPT` in [`workspace_runtime_service.py`](../backend/app/domain/services/workspace_runtime_service.py)); when null or empty, the default is used. Temporal context and capability lines are always appended automatically regardless of whether the base is default or custom. The Pipeline panel in the UI exposes this field with a "Reset to default" button. **`process`** is an ordered list of steps (max 8) that run between execute and compose: **`id`**, **`kind`** (one of `review`, `critique`, `summarize`, `investigate`, `analyze`), **`enabled`**, **`description`** (guides the LLM on desired output), optional **`model`**, **`max_iterations`** (review only; 1–10, default 3), **`questions`** (investigate only; list of strings, max 20), **`expose_in_traces`**. SSE emits `process:{step.id}` started/completed events. **`post_compose`** is an ordered list of steps: **`id`**, **`enabled`**, **`system_prompt`** (template; placeholders such as **`{{reply_text}}`**, **`{{user_message}}`**, **`{{execution_summary}}`**, **`{{composed_reply}}`**, **`{{stream_text}}`**, **`{{last_output}}`**), optional **`model`**, **`output_key`** (string stored on **`delivered_response.delivery_metadata`** alongside **`streamed: true`**), **`replace_streamed_reply`** (if true, SSE **`token`** text uses that step’s output), **`expose_in_traces`** (include a preview in **`composition_result.debug.post_compose`**). **`PUT /workspaces/{id}`** returns **422** if the blob is invalid (e.g. duplicate **`post_compose`** ids, too many steps, oversized strings). Domain module: [`backend/app/domain/workspace/companion_pipeline_config.py`](../backend/app/domain/workspace/companion_pipeline_config.py).

**Per-session isolation:** Rolling memory and summary-merge operate **only** on the `workspace_sessions` row whose id is in the stream URL. The backend does not read **`active_summary`** from other sessions. Clearing the chat UI alone does **not** reset memory; use **New chat** (new session) or **`POST /workspaces/{id}/sessions`** and point the client at the new **`session_id`**.

**Custom Skills** in the UI are workflow definitions with **`expose_as_custom_skill`**; they use the same storage and runtime path as other workflows.
