# Workflow skills — output and diagnostics

Integration skills (Gmail, Calendar, etc.) return a **dictionary** `NodeRunResult.output` with a stable, workflow-facing shape. For debugging and for inspecting vendor truth in the editor, the executor may also attach **`details.skill_diagnostics`**.

### Output explorer (`details.output_explorer`)

The workflow editor can show a **typed output shell** (header, optional capped rows, modal drill-down) instead of relying on a raw JSON tree alone. That view is driven by **`details.output_explorer`**: a **versioned** object (`version: 1`, `kind`, `summary`, `items`) generated in the backend and **not** part of the downstream data contract. Gmail and Calendar list skills use **`kind`** values `gmail_list_messages` and `calendar_list_events`; list/dictionary primitives, **`start_outputs`** (multi-slot **Start**), and other node kinds use additional **`kind`** values. For **persisted run logs**, explorer rows are derived **after** [`run_log_redaction`](../backend/app/core/run_log_redaction.py) so content stays consistent with redacted JSON. Legacy logs may still carry **`details.skill_explorer`** (same shape); the SPA reads **`output_explorer` first**, then that key. See **[`docs/OUTPUT_EXPLORER_UI.md`](OUTPUT_EXPLORER_UI.md)** for the schema, `kind` registry, and how to add new kinds.

### `details.resolved_inputs` (Last Run / Run logs)

- **Purpose:** JSON-serializable map of the **inputs the step actually used** (handles + inline node fields + derived values such as the final Gmail **`q`** string). Used by the workflow editor **Last Run** and **Run Logs** **Inputs** section ([`RunInputsExplorer`](../frontend/src/components/workflow-editor/RunInputsExplorer.tsx): **one [`OutputExplorer`](../frontend/src/components/workflow-editor/OutputExplorer.tsx) card per key** via [`clientOutputExplorerForInputField`](../frontend/src/domain/clientOutputExplorerForInputField.ts); merged with legacy top-level LLM keys via [`lastRunInputsPayload`](../frontend/src/components/workflow-editor/lastRunInputsPayload.ts)). **Not** part of the downstream graph contract.
- **Coverage:** The executor sets **`resolved_inputs`** for primitives, utilities, controls, Start/Stop, For loop, **For Loop End** (aggregated **`exports`** map), workflow refs, Simple LLM (prompts, model, temperature, optional structure schema), Gmail List, and Calendar List (including error paths where inputs are known). **General utilities** such as **Dictionary value by key**, **Read document property**, **List item by index**, **String to List**, **String Trunc** (`string_trunc`), and **Int to String** return structured errors with **`resolved_inputs`** (or safe snapshots like key lists) instead of bare exceptions so **Inputs** still appears on failure. **Sandbox utilities** (`sandbox_*`, **Decision action**, **Sandbox tick** primitive, legacy **Sandbox behavior**) attach **`resolved_inputs`** on validation and runtime errors whenever the step had enough context to resolve inputs (e.g. wired **`sandbox_tick`**, **`action`**, **`target_item_id`**) so **Last Run** and **Run Logs** show the **Inputs** section next to the error for troubleshooting.
- **Stop `output` typing:** If **Stop** `required_outputs[0].type` is **list**, **dictionary**, **int**, or **boolean**, the step’s **`output`** is **`ListNodeOutput`** / **`DictionaryNodeOutput`** / **`IntNodeOutput`** / **`BooleanNodeOutput`** (same shapes as primitives), not **`StopNodeOutput`** with stringified JSON in **`text`**. That keeps **List → Stop → Workflow** (and similar) type-correct. **String** stops still emit **`StopNodeOutput`** with **`text`**. When the required type is **list**, a single upstream **`DictionaryNodeOutput`** whose **`data`** looks like Gmail’s **`{ "messages": [...], "resultSizeEstimate": ... }`** is normalized to **`ListNodeOutput`** with **`data == messages`** (and multi-upstream Stop resolution prefers that shape over a non-matching wire). Plain **`ListNodeOutput`** upstream is unchanged.
- **Workflow → Workflow:** When a **Workflow** node’s output feeds another **Workflow** node, **`details.resolved_inputs.input_overrides`** for the child run uses the same plain Python values (lists/dicts, etc.) as the upstream output—**not** JSON strings for structured data (see `node_output_to_input_override_value` in [`workflow_executor/inputs.py`](../backend/app/domain/workflow_executor/inputs.py)).
- **Redaction:** Persisted logs recurse through `details` with [`run_log_redaction.redact_prompt_like`](../backend/app/core/run_log_redaction.py); keys containing **`prompt`**, **`additional_context`**, or **`user_role_message`** (including inside **`resolved_inputs`**) are redacted at rest like other prompt-like fields.

### String Trunc — utility `string_trunc`

Wires **`target_string`** (string), **`start_index`** (int, non-negative), and **`end_index`** (int). Indices are **0-based**. If **`end_index`** is **`-1`**, the result is the substring from **`start_index`** through the end of the string. Otherwise **`end_index`** is **inclusive** (the slice is `text[start_index : end_index + 1]`). If **`end_index ≥ 0`** and **`end_index < start_index`**, the step errors. Any **`end_index`** less than **`-1`** errors. Output is **`StringNodeOutput`** on handle **`output_string`**. For **Last Run** / persisted logs, **`details.resolved_inputs`** always includes **`target_chars`** and **`result_chars`**; when the target is longer than **4096** characters, the full **`target_string`** is omitted and **`target_truncated`** + a short **`target_prefix`** are recorded instead.

### Dictionary primitive — multiple wires to **items**

When the **Dictionary** primitive has one or more **incoming data edges** (any `target_handle` other than **`trigger`**), the executor **merges** them in persisted edge order:

- **Dictionary** upstream (`DictionaryNodeOutput`): shallow-merge inner `data` with `dict.update` (later keys overwrite).
- **Other** outputs (e.g. **Start** int/string/boolean slots, **Int**): stored under **`data[source_handle]`**, where **`source_handle`** is the **source handle id** (for **Start**, this is each slot’s **`key`** in [`RequiredInput`](../backend/app/domain/schemas/graph_io.py)). If `source_handle` is missing or blank, the key **`output`** is used. If that key is already present (e.g. several parallel wires all use **`output`**), the executor uses **`{source_handle}_{source_node_id}`** so each wire keeps a distinct entry.
- **Trigger** edges (`target_handle` → `trigger`) do not contribute to the dictionary payload.

When there are **no** data edges, the primitive uses its static **`data`** field only.

### Document primitive — `DocumentNodeOutput`

The **Document** primitive (`primitive_type: "document"`) loads a row from **`documents`** by **`data.document_id`** (same visibility as CRUD). It emits **`DocumentNodeOutput`** with **`kind: "document"`** and fields **`id`**, **`name`**, **`description`**, **`markdown`** (**stored body text**; the wire name is historical—bytes may be Markdown, JSON, or other text the workflow interprets). For downstream wiring, **`node_output_to_input_override_value`** and multi-handle resolution expose a **plain dict** that includes **`body`** as an alias for **`markdown`**, so utilities can read **`target_property: "body"`** consistently. The same shape is emitted by **`load_document`** and **`upsert_document`**. In the **Build** editor, connections from **Document** / **Load Document** / **Upsert Document** outputs into **`required_inputs`** slots typed **`string`** or **`any`** are allowed (e.g. **Simple LLM Call** **User Prompt** / **Add context**, string utilities, **Stop** with **`string`** or **`any`** output); at runtime, **`string`** targets receive the **document body only** (**`markdown`** text), while **`any`** still receives the full dict (for sub-workflow bridging and tools that expect the whole object).

### Image primitive — `DictionaryNodeOutput`

The **Image** primitive (`primitive_type: "image"`) holds a user-owned **`url_snapshot_artifacts`** row. Optional wired **`image`** input (**full** **`capture_url_snapshot`** dictionary or a **flat** ref with **`artifact_id`**) **overrides** a manual **`data.artifact_id`** (e.g. after uploading a file via **POST** `/api/v1/url-snapshot-artifacts` with multipart **`file`** — PNG, JPEG, or WebP). Execution emits **`DictionaryNodeOutput`** with **`artifact_id`**, **`mime_type`**, **`width`**, and **`height`** only (no resizing, OCR, or interpretation). Downstream **Multimodal LLM** can wire **`output`** directly to the **`images`** handle; the executor passes dictionary-shaped image outputs through to **`normalize_images_input`**.

### Read Document Property — utility `read_document_property`

Resolves a wired **`document`** input (**`DocumentNodeOutput`** or compatible dict), reads **`target_property`** (also wireable or static) as a key on that dict—e.g. **`body`**, **`name`**, **`description`**, **`id`**—and emits a typed output per **`output_value_type`** (**`string`**, **`list`**, **`dictionary`**, **`boolean`**, **`int`**, **`any`**), same coercion pattern as **Dictionary Value by Key**. Missing keys or type mismatches fail the step.

### Load Document — utility `load_document`

Resolves exactly one of **`document_id`** or **`document_name`** (inline or wired). Loads the row via **`DocumentService`** and emits **`DocumentNodeOutput`**. **`resolved_inputs`** record lookup mode and ids/names (not full body text).

### Upsert Document — utility `upsert_document`

**Inverse of the Document primitive** (which loads a saved row by id): this step **writes** text into **`documents`** and returns the same **`DocumentNodeOutput`** shape. Requires **`name`** and **`content`**. Use it to **save a string as a document**—for example, a multi-line transcript (`"Speaker: …"` per line): wire the assembled string to **`content`**, set **`name`** to a new or existing document title (**`name`** must be unique among documents visible to the run’s user; system-owned names cannot be overwritten). Optional **`existing_document_id`** targets a user-owned row by id; otherwise lookup is by **`name`** (create if missing). **`write_mode`**: **`replace`** (default—replace body; usual for “save full transcript”), **`append`** (append after existing body with `\n\n`), or **`merge_json`** (existing body and incoming **`content`** must parse as JSON **objects**; deep-merge with incoming keys winning; stored body is deterministic JSON text). Failures surface as step errors with safe **`resolved_inputs`** (e.g. **`content_chars`**).

### Parse Document Body — utility `parse_document_body`

Wires a **`document`** input; parses **`body`** / **`markdown`** text as JSON. Root must be an **object** or **array** (emits **`DictionaryNodeOutput`** or **`ListNodeOutput`** respectively); scalars fail.

### Write Object to Document Body — utility `write_object_to_document_body`

Requires **`value`** (dict or list). Emits **`StringNodeOutput`** with **`json.dumps(..., sort_keys=True, ensure_ascii=False)`** and stable separators (same family as other deterministic JSON in the executor).

### Append Value to Document — utility `append_value_to_document`

Wires **`document`** and **`value`**. Appends a serialized chunk to the body text **in memory** (does not persist); use **Upsert Document** to save.

### Validate Against Structure — utility `validate_against_structure`

Requires a JSON Schema: wire a **`structure`** input and/or set **`data.structure_id`** on the node. Validates **`value`** with **`jsonschema.Draft202012Validator`**. Success passes through the instance as the appropriate primitive output type; failure is a step error with a short message.

### Simple LLM Call — what goes to the model vs what you see in **Inputs**

- **Persona** supplies **`persona_system_prompt`** (the text from the Persona record) plus **`model`** and **`temperature`**.
- **Structure schemas (structured output):** When a Structure is used for structured output, the executor may normalize the JSON Schema before sending it to the model (see [`schema_normalizer.py`](../backend/app/domain/workflow_executor/schema_normalizer.py)). For example, JSON Schema allows `type` as an array (e.g. `["string", "null"]`); at runtime, `type` arrays are simplified to a single type (first non-null) so the same stored Structure works across providers without editing the record.
- **HTTP timeout:** Chat completion requests use **`LMSTUDIO_CHAT_TIMEOUT`** (default **3600** seconds / 1 hour in [`config.py`](../backend/app/core/config.py)). Large local models or long structured JSON outputs may need that headroom; set a lower value in `.env` if you prefer faster failure on hung requests.
- **Role=system** payload (**`system_prompt`**): the Persona text, with **additional context** (inline field and/or **Add context** handle) appended after one blank line when non-empty. No other text is added.
- **Role=user** payload: the resolved **user prompt** only (**`user_role_message`** matches **`user_prompt`** in **`resolved_inputs`**).
- **Parallel For Loop cold-start (400 from LM Studio):** When a sub-workflow runs **Simple LLM Call** inside a **For Loop** with **`iteration_mode: parallel`** or **`parallel_iterations: true`**, the first iteration pays the model-load cost and subsequent iterations reuse the warm model. If LM Studio returns a transient **400** with a warmup-shaped body (**`"Model not loaded"`**, **`"No runtime is loaded"`**, **`"Model is warming up"`**, etc.) during that cold-start window, [`_post_chat_completions`](../backend/app/providers/lmstudio.py) retries within **`LMSTUDIO_CHAT_RETRY_BUDGET_SECONDS`**. Non-warmup 400s (unknown model id, bad Structure schema, prompt too long) are surfaced with the LM Studio response body in the step error so **Last Run** / **Run Logs** show the actual reason instead of a generic httpx message. See **[OPERATIONS.md](OPERATIONS.md#local-llm-timeouts-simple-llm-call--lm-studio)** ("400 from LM Studio") for the full marker list and retry semantics.
- **Gmail-shaped messages → string `user_prompt`:** When the **user prompt** slot is typed **string** and the upstream value is a workflow Gmail message dict (curated list item or **`GmailNodeOutput`**), the executor sends a **compact JSON text** of **`id`**, **`threadId`**, **`subject`**, **`from`**, **`to`**, **`date`**, and **`body_text`** (plain body), or **`snippet`** when there is no body — not the full wire object (e.g. **`labelIds`**, **`internalDate`**, flags) so the model sees less noise. Those slim string fields are passed through the shared **text-noise filter** ([`app/core/text_noise.py`](../backend/app/core/text_noise.py)) so invisible / format Unicode (U+034F, zero-width spaces, bidi overrides, category `Cf`) and runaway whitespace are removed even when the upstream `body_text` was authored or pre-processed elsewhere. Header-style fields (**`subject`**, **`snippet`**, **`from`**, **`to`**, **`date`**) are already pre-cleaned at extraction time by **`EMAIL_HEADER_NOISE_FILTER`** in [`workflow_executor/diagnostics.py`](../backend/app/domain/workflow_executor/diagnostics.py), so the slimmer's pass over them is a no-op for content that originated from the Gmail skill. **`output.data`** on other nodes is unchanged; only the string sent to the LLM is slimmed (see [`gmail_llm_prompt.py`](../backend/app/domain/workflow_executor/gmail_llm_prompt.py)).
- **Document → string `user_prompt` / `additional_context`:** When **`user_prompt`** or **`additional_context`** is typed **`string`** and the upstream is **`DocumentNodeOutput`** (or compatible), [`inputs.py`](../backend/app/domain/workflow_executor/inputs.py) passes the stored **body** (**`markdown`**) as plain text to the model — not the full document dict.

### Multimodal LLM — skill `multimodal_llm`

- **Purpose:** Same Persona, optional **Structure** / structured output, and LM Studio chat path as **Simple LLM Call**, but the **user** message is built in OpenAI-compatible **multimodal** form: text plus **`image_url`** parts with `data:{mime};base64,...` payloads. **Images are never stripped** for a text-only fallback; if the loaded model or runtime rejects vision input, the step fails with a structured error.
- **Inputs:** **`user_prompt`** (required; alias **`prompt`** in `required_inputs` is accepted). **`images`** (required **`list`** after normalization): each list element is either **`{ "artifact_id": "<uuid>", ... }`** (UUID of a user-owned **`url_snapshot_artifacts`** row) or a full **`capture_url_snapshot`** output object **`{ "image": { "artifact_id", "mime_type", "width", "height" }, "final_url", ... }`** — the executor reads **`image.artifact_id`** per element. A single top-level object (snapshot-shaped or plain ref) is coerced to a one-element list. Optional **`additional_context`** and **Structure** behave like Simple LLM Call (**`user_prompt`** / **`additional_context`** may be wired from a **Document** / **Load Document** / **Upsert Document** output; **`string`** slots receive the document body text). Optional **`model`** on the node overrides the Persona’s **`default_model`**.
- **Output:** **`ResponseNodeOutput`** (`text` + optional `metadata`) for free-form replies, or **`DictionaryNodeOutput`** when a Structure is in effect. **`metadata`** may include **`model`**, **`usage`**, and **`image_artifact_ids`** (resolved ids for replay/debug). **`resolved_inputs`** do not embed raw image bytes—only ids and safe image metadata.
- **Pairing with URL snapshot:** Typical pattern: **Start** → **`capture_url_snapshot`** → **Multimodal LLM** (wire snapshot **`image`** or a list of **`artifact_id`** objects) → **Stop**. You can also insert an **Image** primitive between capture and **Multimodal LLM** to normalize to the flat artifact object, or use **Image** alone with a file upload or seeded artifact id. For tests or offline samples, you can seed a **`url_snapshot_artifacts`** row (e.g. tiny PNG) and reference it from a **List** primitive instead of running Playwright.
- **Structured errors (non-exhaustive):** **`MISSING_IMAGE_INPUT`** (no images after resolution), **`INVALID_IMAGE_REFERENCE`** (missing or other-user artifact), **`UNSUPPORTED_IMAGE_FORMAT`** (MIME/magic mismatch), **`MODEL_NOT_MULTIMODAL`** when LM Studio (or compatible) indicates the selected model cannot accept image content (**`retryable: false`**). Other provider failures use the same surfacing as Simple LLM Call (timeouts, 429, etc., where classified).
- **Replay / overrides:** **`workflow_output_overrides`** for this node use the same shape as Simple LLM Call (`ResponseNodeOutput`-compatible text) for substituting the model reply in automation.

### Text-to-Speech — skill `text_to_speech`

- **Output:** **`AudioNodeOutput`** (`kind: audio`, **`mime_type`** default **`audio/wav`**, **`audio_base64`** WAV bytes). **Stop** may declare **`required_outputs[0].type: audio`** to pass audio through typed coercion.
- **Data:** **`tts_model_id`** (UUID of a **`ready`** row in **`tts_model_artifacts`**), optional **`voice_sample_id`** (UUID of the current user’s **`voice_samples`** row — voice **clone**), optional **`engine`** override (must match the registry row’s **`engine`** when set), **`tts_options`** (opaque JSON object per engine), **`required_inputs`** with **`text`** (string).
- **Voice clone:** When **`voice_sample_id`** is set, the executor loads the sample (must belong to the run’s user), sends **`ref_audio_base64`** (WAV) and **`ref_text`** into bridge **`options`**, and passes the **workflow text** as **`text`**. The TTS bridge decodes that base64 to audio samples before calling Qwen (so strings that contain **`/`** are not mistaken for file paths). **`ref_text`** should match what was spoken in the saved clip (same as in **Voice samples**). Use a **Base** / clone-capable **`qwen_torch`** artifact on the node; **Voice Design** checkpoints are for design-style synthesis and **Voice samples → Generate**, not this path. In clone mode, **`speaker`** and other **CustomVoice**-style **`tts_options`** are ignored by the bridge.
- **Bridge:** Synthesis uses [`synthesize_wav`](../backend/app/providers/tts_bridge.py) (`POST /v1/tts` on the bridge). **`resolved_inputs`** include **`user_prompt`** (the text), **`tts_model_id`**, **`engine`**, **`display_name`**, and **`voice_sample_id`** when a sample is selected.
- **Editor playback (not executed on the server):** Per node and in **My Settings → View Settings**, **`tts_playback_when`** is **`inline`** (play each clip when the node finishes), **`manual`** (only the run log / inspector player), or **`after_workflow`** (queue successful clips and play them **in `step_number` order** when the run ends with overall status **`ok`**; the queue is **discarded** on error or **`partial`**). Legacy **`data.auto_play_tts_on_node_end`** (**`true`** / **`false`**) is still read when **`tts_playback_when`** is omitted. Omit or **`null`** on the node to follow the user default. Autoplay uses a programmatic **`HTMLAudioElement`** ([`ttsAudioPlayback.ts`](../frontend/src/domain/ttsAudioPlayback.ts)): **`NotAllowedError`** still surfaces a clear toast (use Run logs / Download); **`AbortError`** or a media **`error`** after playback has demonstrably started—detected via **`playing`**, fulfilled **`play()`**, **`timeupdate`**, **`currentTime`**, or **`played`** ranges—are treated as non-fatal so the UI does not show **“Could not play TTS audio”** when you already heard the clip. **`inline`** clips and the **`after_workflow`** queue share one autoplay promise chain so **`play()`** never overlaps between modes in the same run.
- **Logs:** [`run_log_redaction`](../backend/app/core/run_log_redaction.py) treats **`audio_base64`** like other sensitive payload keys at rest. Live **`node.completed`** (**SSE**) payloads still carry base64 for editor playback. While a **Build** run is connected, **`GET …/workflow-runs/{id}/events`** may **re-emit** persisted **`node.completed`** rows from the DB (for tail sync / reattach); those replays use redacted output. The workflow editor keeps the **in-memory live** row for **Last Run** when the replay is a duplicate of the same **`step_number`** with **`audio_base64: "[redacted]"`**, so the inspector player and inline autoplay are not replaced or re-triggered until you clear Last Run or start another run. The **inline player and Download** appear in **Run logs**, the editor **Last Run → Output** inspector, and **Replays** (Explore) for the same live payload (same browser session). There is **no** WAV file written to disk by the app; to keep a file, use **Download** on the audio row. **Older runs** loaded from history typically **do not** include audio bytes—re-run to hear. **My Settings** defaults **`tts_playback_when`** to **`inline`**; browsers often block auto-play without a recent user gesture—when playback fails, use the inline control or **Download**.

### Voice input (transcribe) — skill `transcribe_audio`

- **Where it runs:** Use **Run** from the workflow editor so the client subscribes to **`GET /api/v1/workflow-runs/{run_id}/events`** (**SSE**). The executor emits **`input_required`** (with **`kind`: `transcribe_audio`**) before it waits; the SPA records audio (**Talk** / **Stop**) and **POSTs** multipart audio to **`POST /api/v1/workflow-runs/{run_id}/transcribe-audio`**. Do **not** use sync **`POST .../run`** for graphs that contain this node unless every such node has an **`output_overrides`** entry (automation only).
- **Output:** **`StringNodeOutput`** — the transcript as **`text`** (same as other string-producing steps). Optional segment metadata may appear in step **`details`** (not the primary `output` wire).
- **Data:** optional **`language`** (Whisper / BCP-47 code), optional **`task`** — **`transcribe`** (default) or **`translate`** (to English), optional reserved **`model`** for future bridge overrides.
- **Bridge:** The API calls the **STT bridge** ([`services/stt-bridge/`](../services/stt-bridge/)) via [`stt_bridge.py`](../backend/app/providers/stt_bridge.py) after audio is uploaded. Weights and GPU stay out of the main API process; see [OPERATIONS.md](OPERATIONS.md#speech-to-text-stt-bridge).
- **Ops note:** The pending “deliver audio for this run step” registry is **in-process** (single **uvicorn** worker / local dev). Multi-worker deployments would need a shared store or sticky sessions (future work).

### Audio File Input (transcribe) — skill `audio_file_input`

- **Purpose:** Select an existing audio file and transcribe it through the same **STT bridge** used by **Voice input**. This adds a file source path only; it does **not** introduce a separate transcription system.
- **Where it runs:** If `data.audio_artifact_id` references a user-owned saved audio artifact, the executor reads that file and can run from sync **`POST …/run`** or a **Build** run (**`POST …/runs`** + **`GET …/events`**). If no artifact is configured, use **Run** from the workflow editor so the client opens the **events** stream; the executor emits **`input_required`** (**`kind`: `audio_file_input`**) and waits for the SPA to upload a file to **`POST /api/v1/workflow-runs/{run_id}/audio-file-input`**.
- **Output:** **`StringNodeOutput`** — the transcript as **`text`**, matching **Voice input**. File metadata stays in step **`details`**, not the downstream wire contract.
- **Data:** optional **`audio_artifact_id`** (UUID from **`/api/v1/audio-file-artifacts`**), optional **`language`**, optional **`task`** — **`transcribe`** (default) or **`translate`** (to English), optional reserved **`model`** for future bridge overrides.
- **Artifacts:** **`POST /api/v1/audio-file-artifacts/`** accepts multipart audio for the current user and stores bytes in the API database. Initial accepted formats are **MP3**, **WAV**, **M4A**, **OGG**, **FLAC**, and **WEBM**, capped by **`STT_MAX_AUDIO_UPLOAD_BYTES`**. Saved artifacts are never embedded in node outputs or run logs.
- **Details:** `details.resolved_inputs` includes **`source_type`**, **`filename`**, **`mime_type`**, **`size_bytes`**, optional **`audio_artifact_id`**, **`task`**, **`language`**, **`transcribe_language`**, and **`transcript_chars`**. STT **segments** and **duration_seconds** mirror the Voice input details shape.
- **Programmatic e2e:** From `backend/`, `uv run python scripts/run_audio_file_input_workflow_http_e2e.py` starts a local FastAPI server, logs in over HTTP, creates the workflow through the API, **`POST …/runs`** + **`GET …/events`**, and posts multipart audio to **`/workflow-runs/{run_id}/audio-file-input`** while the SSE connection is open. By default it mocks STT and uses a tiny WAV, so no external service calls are made. Use `--real-stt --audio-file /path/to/file.wav` to exercise the bridge with a real file. `scripts/run_audio_file_input_workflow_e2e.py` remains a lower-level executor sanity check.

### Transcribe File (provider-abstracted) — skill `transcribe_file`

- **Purpose:** Provider-abstracted speech-to-text that emits a **rich Transcript primitive** (segments, optional words & speakers) instead of a plain string. Lives alongside **Voice input** and **Audio File Input** without replacing them, so existing graphs are untouched. V1 ships two backends: **`local_whisper`** (the existing **STT bridge**, runs on-device) and **`assemblyai`** (cloud STT). Additional providers can be registered by adding a `SpeechTranscriptionProvider` subclass to [`app/providers/transcription/`](../backend/app/providers/transcription/).
- **Where it runs:** If `data.audio_artifact_id` is set, the executor reads the saved artifact and runs from sync **`POST …/run`** or a **Build** run (**`POST …/runs`** + **`GET …/events`**). If no artifact is configured, use **Run** from the workflow editor so the client opens **`GET …/workflow-runs/{run_id}/events`**; the executor emits **`input_required`** (**`kind`: `transcribe_file`**) and the SPA uploads bytes to **`POST /api/v1/workflow-runs/{run_id}/transcribe-file-input`** (mirrors the Audio File Input route). Long-running cloud jobs are persisted in `transcription_jobs` and survive client disconnects: a background **lifespan poller** advances the row, and the SPA **reopens the same `…/events`** URL to **replay** persisted state and **tail** live updates.
- **Output:** **`DictionaryNodeOutput`** whose `data` is a `TranscriptPrimitive` dict — `{ type: "transcript", version, full_text, language, duration_seconds, provider, segments[], words[], metadata }`. See [`app/domain/schemas/transcript.py`](../backend/app/domain/schemas/transcript.py) for the canonical shape. Downstream nodes consume the **same** dict regardless of provider, so swapping the provider does not break wiring.
- **Data:** **`provider`** (`local_whisper` \| `assemblyai`; default `local_whisper`), optional **`provider_model_id`** (primary speech-model slug for that provider when the directory lists models; omit or empty to use deployment defaults such as **`ASSEMBLYAI_SPEECH_MODELS`** for AssemblyAI), optional **`audio_artifact_id`**, optional **`language`** (BCP-47), **`task`** — `transcribe` (default) or `translate` (Whisper translates inline; AssemblyAI surfaces the request via `metadata.provider_metadata` without auto-translating), optional **`prompt`** (used as bias text/word-boost depending on provider), boolean **`diarization_enabled`**, boolean **`include_word_timestamps`**.
- **Provider directory:** **`GET /api/v1/transcription/providers`** returns the list of providers the deployment exposes in the editor (see **`TRANSCRIPTION_PROVIDERS_ENABLED`** in [`config.py`](../backend/app/core/config.py); defaults include **`local_whisper`** and **`assemblyai`**). Each item may include a **`models`** array (`id`, `label`, optional `description`, `is_default`) for the second inspector dropdown. The editor shows a privacy/key notice per provider.
- **API keys:** AssemblyAI keys are stored per-user via **My Settings → API Settings** (`assemblyai`), encrypted at rest with the standard `user_api_keys_crypto` mechanism — same pattern as OpenAI/Anthropic/Google keys. Server-wide fallback **`ASSEMBLYAI_API_KEY`** in env is only consulted when no per-user key is set.
- **Persistence:** A `transcription_jobs` row is written **before** the provider call so a process crash mid-submit leaves a recoverable breadcrumb. Runtime uploads to async providers spill to a `transient=true` `audio_file_artifacts` row (hidden from "My Audio Files") so the poller can advance the job without re-uploading. Terminal jobs delete the transient artifact automatically.
- **Programmatic e2e:** From `backend/`, `uv run python scripts/run_transcribe_file_workflow_e2e.py` exercises both providers and both source modes against the in-process executor with mocked externals (saved artifact + `local_whisper`, runtime upload + `local_whisper`, saved artifact + `assemblyai`). Pass `--real-stt --audio-file …` or `--real-assemblyai --assemblyai-key … --audio-file …` to drive the live bridges. The HTTP twin `scripts/run_transcribe_file_workflow_http_e2e.py` starts a local FastAPI server, logs in over HTTP, exercises both providers through **`POST …/runs`** + **`GET …/events`**, and verifies **SSE replay/tail** matches persisted **`transcription_jobs`** state.

### URL snapshot (rendered page) — skill `capture_url_snapshot`

- **Where it runs:** The Mind Weave API process drives **headless Chromium** via **Playwright** to **navigate** to the configured **`url`**, wait per **`wait_until`**, then **screenshots** a **PNG** and stores it as a per-user **artifact**. This is a **perception** step only: it does not parse the DOM, extract text, classify content, or judge whether the page is “useful.” A successfully captured bot wall or interstitial is still a **valid** result. For raw HTTP bodies (no rendering), use **`fetch_url`**; wire both in graphs when you need HTML text **and** a visual capture.
- **Output:** **`DictionaryNodeOutput`**. On success, **`output.data`** includes **`image`**: `{ artifact_id, mime_type, width, height }` (PNG; **`mime_type`** is **`image/png`**), plus **`final_url`** (after redirects), **`captured_at`** (RFC3339 UTC), **`duration_ms`**, and **`cached`**. On transport/browser failure the step still **succeeds** with an **`error`** object **`{ type, message, retryable }`** plus **`captured_at`**, **`duration_ms`**, **`cached: false`**—same outer-step pattern as **`fetch_url`**.
- **Inputs (node `data`):** **`url`** (static or **required_inputs** wire), **`full_page`** (boolean, default **true**), optional **`viewport_width`** / **`viewport_height`** (positive integers; if omitted, server defaults from config—stable viewport for reproducibility), **`wait_until`**: **`load`** (default) \| **`domcontentloaded`** \| **`networkidle`**, optional **`timeout_ms`** (else **`CAPTURE_URL_SNAPSHOT_DEFAULT_TIMEOUT_MS`** in [`config.py`](../backend/app/core/config.py)), **`cache_policy`**: **`default`** \| **`refresh`** \| **`bypass`**.
- **Cache / replay:** Per-user **`url_snapshot_caches`** maps a **deterministic `cache_key`** (SHA-256 of normalized JSON: **url**, **full_page**, **viewport** width/height, **wait_until**) to a **`url_snapshot_artifacts`** row. **`default`** — return cached capture when present; **`refresh`** — always re-capture and replace cache entry; **`bypass`** — always re-capture and **do not** update the cache table (the new run still stores an **artifact** for that execution). **`output_overrides`** replays the same as other skills: JSON object coerced to **`DictionaryNodeOutput`**.
- **Artifacts API:** `GET /api/v1/url-snapshot-artifacts/{artifact_id}` returns **`image/png`** for the current user’s row. Used by the editor / output explorer; **not** a public CDN.
- **Security / ops:** Navigation runs wherever the **API** runs, same class of **SSRF** / private-network reachability as **`fetch_url`** (see that section). Deploy hosts need **Chromium** for Playwright: run **`playwright install chromium`** (or your image’s equivalent). See [OPERATIONS.md](OPERATIONS.md#capture_url_snapshot--playwright).

### Fetch URL — skill `fetch_url`

- **Where it runs:** The Mind Weave API process performs an **HTTP** request (via **httpx**) to the configured **`url`**, using optional **`method`** (default **GET**), optional **`headers`**, and optional **`timeout_ms`** (else **`FETCH_URL_DEFAULT_TIMEOUT_MS`** in [`config.py`](../backend/app/core/config.py), default 30s). This is a **perception** step: it does not parse HTML, extract “main content,” or follow links beyond normal HTTP redirects. For HTML pages, wire **`body`** (string) into the **`html_parse_basic`** utility if you need a small structured object (`title`, `text_blocks` as `{tag, text}` items, `links`) before LLM steps—see [WORKFLOW_TOOL_INVENTORY.md](WORKFLOW_TOOL_INVENTORY.md) (`html_parse_basic`).
- **Output:** **`DictionaryNodeOutput`**. On a completed HTTP response, **`output.data`** includes **`status_code`**, **`final_url`** (after redirects), **`headers`** (lowercased header names → string values), **`body`** (decoded text; responses larger than **`FETCH_URL_MAX_BODY_BYTES`** fail as a structured transport error, not a partial body), **`fetched_at`** (RFC3339 UTC), **`duration_ms`**, **`cached`**. **Non-2xx** responses still **succeed the step**; branch downstream using **`status_code`**. If the request cannot complete (timeout, connection, etc.), the step still **succeeds** with an **`error`** object **`{ "type", "message", "retryable" }`** and without HTTP fields—suitable for conditional wiring.
- **Cache:** Per-user rows in **`url_fetch_caches`** (see migration **`u8v9w0x1y2z3`**). Cache key: normalized **URL**, **method**, and sorted **headers** map. **`cache_policy`:** **`default`** — use stored successful response if present; **`refresh`** — always fetch and overwrite cache on success; **`bypass`** — always fetch, do not store. This cache is **not** the same as **Build → Replays** (read-only run history).
- **Security / ops:** Requests execute wherever the **API** runs and can reach any **http**/**https** URL the host can (including private networks). v1 does **not** block RFC1918 or metadata hosts; operators should treat graphs as **trusted** or isolate the deployment. See [OPERATIONS.md](OPERATIONS.md#workflow-fetch_url-env).

## `output.data` (downstream contract)

- **Purpose:** What other nodes, tools, and LLM steps consume. Keep fields **documented and reasonably sized**.
- **Do not** rely on undocumented keys; add new fields deliberately and update tests.
- **Voice input** (`transcribe_audio`): primary wire value is the **transcript string** (same as any **`StringNodeOutput`**). Segment-level diagnostics stay in **run** **`details`**, not in **`output.data`**, unless you change the node contract in code and docs.
- **Calendar list events** (`calendar_list_events`): `events` is a list of curated objects (see executor implementation for the current whitelist). **`time_min`** and **`time_max`** are RFC3339 instants passed to Google Calendar **`events.list`** (`timeMin` / `timeMax`). In the **workflow editor**, **Time & limits** uses **native date** and **time** (minute resolution) with wall-clock values interpreted in the user’s **`User.settings.workflow_time_zone`** (**My Profile → Workflow time zone**; `"system"` uses the browser zone)—same family of controls as Gmail List. **Output explorer** formats event **`start`** / **`end`** using that same resolved zone. Open the **info** icon for how wall-clock values become RFC3339 and to see current `time_min` / `time_max`; optional **raw RFC3339** editors match Gmail’s disclosure pattern. Wired handles still override inline values at run time. For **relative** windows (e.g. “five days ago” through **now**), wire **DateTime** with **`use_now`** and the **`add_days`** utility (negative `days`) into those slots instead of static instants.
- **Gmail list messages** (`gmail_list_messages`): the node emits **`ListNodeOutput`** — **`output.data`** is a JSON array of curated **Gmail message** objects (same field shape as the **Gmail** primitive’s wire contract). Each entry is built with **`users.messages.list`** (ids) then **`users.messages.get`** with **`format=full`** (one GET per listed message, bounded by **`max_results`**). Curated fields include **`id`**, **`threadId`**, **`snippet`**, **`labelIds`**, headers **`subject`**, **`from`**, **`to`**, **`date`**, **`internalDate`** when present, **`body_text`**, and **`body_truncated`** when the body exceeds the configured cap. **`body_text` is the plain text part when present; otherwise HTML is parsed to text** (`<style>` / `<script>` content dropped, tags removed, HTML entities unescaped — raw HTML is **not** included in the wire shape). The plain text is then run through the shared **text-noise filter** preset **`EMAIL_BODY_NOISE_FILTER`** in [`app/core/text_noise.py`](../backend/app/core/text_noise.py). Defaults applied to bodies: line-ending normalization (`\r\n` / lone `\r` → `\n`), HTML-entity unescape (so literal `&zwnj;` / `&nbsp;` / `&#x200B;` collapse with the invisible-Unicode pass), invisible / bidi character strip, repeated layout-separator drop, tracking query-param strip from URLs (allow-list of `utm_*`, `mc_cid`, `mc_eid`, `fbclid`, `gclid`, `_hsenc`, `_hsmi`, `ref`, `aff`, `cid`, `eid`, `mkt_tok`, etc.), long-URL shortening to `[link]` above `long_url_threshold` (120 chars), orphan `[link]` placeholder line drop, conservative marketing/legal footer line drop (`unsubscribe`, `view in browser`, `manage preferences`, `follow us`, `privacy policy`, `copyright ©`), runaway-whitespace collapse, and a final cap at **`max_chars`** (currently **8,000** characters; was 32,768 before the noise filter landed). Short header-style fields (**`snippet`**, **`subject`**, **`from`**, **`to`**, **`date`**) are independently filtered through **`EMAIL_HEADER_NOISE_FILTER`** — invisible-Unicode + entity cleanup + whitespace collapse only, with no truncation, no URL changes, and no footer stripping — so subjects and snippets stop carrying invisible-character padding from marketing senders. Entries may contain **`fetch_error`** if a metadata fetch fails (run still succeeds). The API’s **`resultSizeEstimate`** is surfaced on the step as **`details.gmail_result_size_estimate`** (not in **`output.data`**). See below for **`q`**; diagnostics include **`message_gets`** counts (`attempted` / `ok` / `failed`). To tune the filter, edit `EMAIL_BODY_NOISE_FILTER` / `EMAIL_HEADER_NOISE_FILTER` (or pass an explicit `max_body_chars` to `curated_gmail_message_from_full_api`) — quoted-reply stripping is off by default and can be enabled via `NoiseFilterConfig` flags. **Breaking change (v1):** older runs used **`DictionaryNodeOutput`** with **`messages`** and **`resultSizeEstimate`** on **`output.data`**; graphs and **`output_overrides`** must use a **JSON array** for this skill’s override payload.

- **Gmail primitive** (`primitive_type: "gmail"`): emits **`GmailNodeOutput`** (`kind: "gmail"`) for a single message — static **`message`** object in the node and/or a wired **`gmail`** input. Use **Start** / **Stop** slots typed **`gmail`** for the same shape.

### Gmail list messages — composing `q`

The Gmail API [`users.messages.list`](https://developers.google.com/gmail/api/reference/rest/v1/users.messages/list) only accepts a single search string **`q`** (plus `maxResults`, `pageToken`, optional `labelIds`, optional `includeSpamTrash`). There are **no** separate HTTP parameters for “time range” or “unread only”—those are expressed with Gmail search operators inside **`q`**.

This skill merges:

1. **Structured inputs** (optional): **`unread_only`** → `is:unread`; **`after`** / **`before`** → `after:YYYY/MM/DD` / `before:YYYY/MM/DD` derived from RFC3339 instants. Gmail search is **day-only** for these operators (no time-of-day in **`q`**). The executor picks the **calendar day** using **`User.settings.workflow_time_zone`** when it is a fixed IANA name (not `"system"`); when the profile uses **`system`**, it uses optional **`execution_time_zone`** on **`POST …/run`** or **`POST …/runs`** (the SPA sends the browser’s resolved IANA). If neither yields a zone, it falls back to the **UTC** calendar day. Storing date **and** time as RFC3339 keeps parity with Calendar pickers and matters near midnight when the zoned date differs from UTC. Gmail may still interpret day boundaries in the mailbox’s timezone for search—behavior usually matches the Gmail UI. Power users can edit raw RFC3339 in the inspector disclosure.
2. **Raw `query`** (optional): appended as-is for power users ([Gmail search operators](https://support.google.com/mail/answer/7190)).

Non-empty parts are **space-joined** (implicit AND). Avoid conflicting operators (e.g. `is:read` in `query` while **Unread only** is enabled).

3. **Inbox categories** (optional): After the merge above, the executor may append Gmail **`category:`** operators ([search operators](https://support.google.com/mail/answer/7190)):
   - **Primary only** → `category:primary` (matches the Primary inbox tab).
   - **Exclude tab(s)** → `-category:promotions`, `-category:social`, etc.

   Values come from the **Gmail List** node inspector and/or **My Settings → Google → Gmail workflow filters** (account defaults). Per-node fields override account defaults when set; the node can **skip account category filters** so only the node and raw **Search query** apply.

**`labelIds` vs `category:`:** Message payloads include Gmail system labels such as `UNREAD` or `CATEGORY_PROMOTIONS`. Those correspond to the same tabs the UI uses. Handy mapping:

| `labelIds` value | `category:` slug (in `q`) |
|------------------|---------------------------|
| `CATEGORY_PRIMARY` | `primary` |
| `CATEGORY_SOCIAL` | `social` |
| `CATEGORY_PROMOTIONS` | `promotions` |
| `CATEGORY_UPDATES` | `updates` |
| `CATEGORY_FORUMS` | `forums` |

(`reservations` / `purchases` are also valid `category:` operators per Google’s docs; they may appear in search when enabled for the mailbox.)

Power users can still type `category:…` or `-category:…` in the raw **Search query**; combining with structured **Primary only** / **Exclude** options may duplicate clauses but remains a valid `q`.

The workflow editor shows an **info** control next to **Search query (optional)** with a short operator primer (same substance as below; behavior remains documented here and in Google’s references).

**Diagnostics:** `details.skill_diagnostics.gmail_v1` includes the final **`q`**, **`operation`**: `users.messages.list`, **`gmail_category_filters`** (`effective_inbox_focus`, `effective_exclude_categories`, `skip_account_category_filters`), a **truncated** raw **list** response (`omitted_message_count` when the list is capped for log/stream size), and **`message_gets`** (`attempted` / `ok` / `failed`) for **`users.messages.get`** calls. Full per-message JSON is **not** included in diagnostics by default (size).

## `details.skill_diagnostics` (Explorer / logs only)

- **Purpose:** Full or near-full **vendor API** payloads for the Workflow Editor **Last Run** and **Run Logs** views. **Downstream graph nodes must not depend on this key** — it can be truncated, redacted when persisted, or extended without notice.
- **Structure:** Top-level map keyed by integration id, e.g. `google_calendar_v3`, `gmail_v1`. Each value is an object that includes:
  - **`operation`** — stable string (e.g. `events.list`, `users.messages.list`).
  - **`response`** — JSON-serializable body (or truncated slice of it).
  - **`truncated`** / **`omitted_event_count`** (Calendar) or **`omitted_message_count`** (Gmail) — when list payloads are capped for size.

### Naming

- Use **`{vendor}_{api_version}`** keys (`google_calendar_v3`, not arbitrary strings).

### Size limits

- Truncate large **`items`** / list arrays with explicit `truncated` and `omitted_event_count` so **SSE payloads** / `node_run_logs` rows stay bounded.

### Redaction and storage

- **Live stream / sync `POST …/run`:** `skill_diagnostics` is included **unredacted** in `NodeRunResult` so operators can debug in the UI over HTTPS.
- **Persisted `NodeRunLog` and `GET …/run-logs`:** [`run_log_redaction.redact_prompt_like`](../../backend/app/core/run_log_redaction.py) recurses into `details` and replaces sensitive **key names** (e.g. `summary`, `description`, `location`, `attendees`) with `[redacted]`. Expect **rich trees during the current run**, and **privacy-safe** historical logs.

Implementation merges diagnostics via [`workflow_executor/diagnostics.py`](../../backend/app/domain/workflow_executor/diagnostics.py).

### For Loop — iteration modes (`data.iteration_mode`, legacy `data.parallel_iterations`)

- **`sequential`** (default) — One body pass **per list item**, in order. Same semantics as **`parallel_iterations: false`** / omitted.
- **`parallel`** — Same as **`parallel_iterations: true`** (below): concurrent iterations, isolated maps, **`Add to List`** merge ordering, nested-loop restriction.
- **`batched`** — Runs the body for **`batch_size`** items at a time (default **`WORKFLOW_DEFAULT_LOOP_BATCH_SIZE`**, capped by **`WORKFLOW_MAX_LOOP_BATCH_SIZE_CEILING`** operator env). Still subject to **`User.settings.max_concurrent_lm_studio_calls`** × **`WORKFLOW_MAX_CONCURRENT_*`** layering for overlapping work inside each batch.

Optional **`continue_on_error`** keeps later iterations/schedules advancing after handled body failures (**`summary`** / Explorer surfaces per-item **`errors`** when present). **`max_iterations`** caps how many iterations run even when the list is longer (must still satisfy resolved **`execution_limits.max_loop_iterations`** vs **list length**). A wired **`summary`** handle exposes a **`dictionary`** aggregate when the run collected per-item metadata.

### For Loop — parallel iterations (`data.parallel_iterations`)

- **Default:** Off — the executor runs one full body pass per list item **sequentially** (same as **`iteration_mode: sequential`**).
- **When on:** Same as **`iteration_mode: parallel`** — each list item runs the loop body **concurrently** with an **isolated** output map for that iteration. Upstream nodes outside the body are visible to every iteration (read-only from the shared baseline snapshot).
- **Add to List:** Per-iteration appends are **merged in list index order** (item 0, then 1, …) so the final **`ListNodeOutput`** matches sequential semantics. The **last** recorded **Add to List** run for that loop is updated to show the merged list (parity with sequential runs where carry grew in one dict).
- **For Loop output:** Still the **last list element’s** item shape (same as sequential).
- **Constraints:** A graph with **`parallel_iterations`: true** cannot contain a **nested For Loop** in that loop’s body — validation fails at run time with a clear error. Streaming step order for body nodes may **interleave** across iterations; each event still carries **`details.for_loop_iteration`**.
- **Simple LLM (Persona / Structure DB reads):** When iterations overlap, the executor **serializes** SQLAlchemy **`Session`** reads for **Persona** and **Structure** on **Simple LLM Call** steps; **`await`** LM Studio **`chat`** calls **still run in parallel** across iterations (only short DB reads are serialized).
